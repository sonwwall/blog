# 第二十节：分析服务的特性：我的服务应该开多少个进程，多少个线程？

这一节主要围绕 7 个点展开：

1. 服务应该先按什么维度分析
2. 什么是计算密集型和 I/O 密集型
3. 为什么 I/O 操作不一定会持续占满 CPU
4. 线程数或进程数为什么经常会超过 CPU 核数
5. 应该看哪些指标来判断瓶颈
6. 不同语言和运行时在线程模型上有什么区别
7. 最后到底该怎么确定进程数和线程数

## 1. 先不要急着定线程数，先判断服务是什么类型

当我们问：

- 服务应该开多少个进程
- 服务应该开多少个线程
- 应该给多少 CPU

本质上是在问：

- 这个服务的主要瓶颈到底在哪里

如果服务主要在做计算，那么优化方向和资源配置会偏向 CPU。  
如果服务主要在等磁盘、网络、数据库、日志落盘等 I/O，那么优化方向就完全不同。

所以第一步不是先拍一个线程数，而是先判断：

- **这是一个计算密集型服务，还是一个 I/O 密集型服务**

## 2. 什么是计算密集型和 I/O 密集型

### 2.1 计算密集型

计算密集型服务，指的是应用的大部分时间都花在：

- 算法计算
- 数学运算
- 数据处理
- 编解码
- 压缩解压
- 加密解密

这类任务的特点通常是：

- CPU 长时间处于忙碌状态
- 线程很少因为外部设备而阻塞
- 性能往往直接受 CPU 核数影响

可以先记一个很粗的规律：

- **计算密集型更接近“CPU 跑满多少核，就能干多少活”**

### 2.2 I/O 密集型

I/O 密集型服务，指的是应用的大部分时间都花在：

- 读写磁盘
- 收发网络请求
- 调用数据库
- 打日志
- 等待外部系统返回结果

I/O 的本质，就是：

- 对设备进行读写

比如：

- 读取磁盘数据
- 等待网卡收包发包
- 从键盘读取输入

这类任务的特点通常是：

- CPU 不是一直在算
- 很多时间在等待外部设备完成工作
- 单个线程常常会经历“执行一会儿，再等待一会儿”

因此 I/O 密集型服务不应该只盯着 CPU 使用率，还要看：

- I/O Wait
- 磁盘吞吐
- 网络吞吐
- 下游依赖响应时间

## 3. 为什么读磁盘到内存，不需要 CPU 一个字节一个字节搬

很多人刚学系统时，会以为：

- 磁盘数据进入内存，必须由 CPU 自己一点点搬运

但现代计算机里，通常有一个关键模块：

- `DMA`，也就是直接内存访问 `Direct Memory Access`

它的作用可以简单理解为：

- 让 I/O 设备和内存之间的数据传输，不必完全由 CPU 逐字节参与

CPU 仍然要负责：

- 发起 I/O 请求
- 配置相关控制信息
- 处理中断和状态变更

但真正的大块数据搬运，往往可以由 `DMA` 完成。

这意味着：

- I/O 多，不等于 CPU 一直在做数据拷贝
- CPU 很多时候是在等待 I/O 结果回来

也正因为如此，I/O 密集型程序经常会表现出：

- CPU 没有满载
- 但吞吐还是上不去

## 4. CPU 的时间都去哪了

分析一个服务能不能继续加线程、加进程，本质上是在分析：

- CPU 时间到底被怎么消耗了

通常可以粗略分成几类：

- **忙碌**
- **空闲**
- **被偷走**

其中“忙碌”还可以再拆分为：

- 用户空间程序在运行
- 内核空间程序在运行
- 中断处理程序在运行

而“空闲”里，有一个特别重要的部分就是：

- **I/O Wait**

也就是说：

- CPU 当前没在有效执行计算
- 但也不是纯粹什么都没事干
- 它是在等 I/O 完成

所以看到 CPU 没跑满，不代表系统还有充足余量。  
有时候恰恰相反，是因为：

- 大量线程都卡在 I/O 上

## 5. 为什么线程数或进程数往往会超过 CPU 核数

这是这一节最核心的问题之一。

很多人直觉上会认为：

- 有 8 个核，就开 8 个线程
- 有 16 个核，就开 16 个进程

这个想法只在一种场景下相对成立：

- **纯计算密集型**

因为这类任务只要线程多于 CPU 核数，就会带来更多调度切换，未必有收益。

但真实业务里，大量服务并不是纯计算型，而是：

- 一边执行
- 一边等待 I/O

假设一个线程有一半时间在真正用 CPU，另一半时间在等 I/O，那么只开一个线程时，这个 CPU 核就会有一半时间闲着。  
如果此时再增加一个线程，就有机会在前一个线程等待 I/O 时，让后一个线程把 CPU 用起来。

这就是为什么在 I/O 密集型场景里：

- **线程数和进程数经常会超过 CPU 核数**

本质原因不是“线程越多越好”，而是：

- 希望在一部分线程等待 I/O 时，另一部分线程继续利用 CPU

## 6. 一个常见的估算思路

如果把一个线程平均等待 I/O 的时间占比记作 `P`，  
内存中同时有 `n` 个类似线程，那么可以用一个很常见的近似思路去理解 CPU 利用率：

- `CPU 利用率 ≈ 1 - P^n`

这个公式不用死记，它表达的核心意思是：

- 单个线程等待 I/O 的概率越高，就越需要更多并发执行单元来填补空闲
- 并发线程越多，CPU 空转的概率通常越低

比如如果一个线程 50% 的时间在等 I/O：

- 只开 1 个线程，CPU 可能只能利用一半
- 开到 2 个线程，就可能把更多空闲时间补上

所以在 I/O 密集型服务里，线程数通常会大于核数。  
但这只是一个方向性的理解，不是一个脱离压测就能直接拍板的万能公式。

## 7. 不同语言和运行时，进程线程策略也不同

“开多少个线程、多少个进程”不能脱离具体技术栈。

### 7.1 不一定所有应用都适合“线程数 = 核数”

有些应用天然不是典型的多线程模型，比如：

- `PHP`
- `Node.js`

这类应用里，更常见的是：

- 事件循环
- 异步回调
- 协程
- 多进程扩展

例如 `Node.js` 单个进程通常更偏单线程事件循环模型。  
如果机器有 8 个核，那么更常见的思路往往是：

- 开多个进程
- 让不同进程分别利用不同核心

### 7.2 Java 和 Go 的线程模型也不同

`Java` 更接近：

- 一个应用线程，对应一个内核线程的 `1:1` 模型

所以线程数增加，往往会比较直接地影响：

- 内核调度开销
- 栈空间占用
- 上下文切换成本

`Go` 则有自己的轻量级线程模型：

- `goroutine`

它不是简单地一个业务线程对应一个内核线程，而是：

- 多个轻量级线程复用少量内核线程

因此在 `Go` 里讨论“线程数量”，往往要分清楚：

- 业务协程数量
- 运行时工作线程数量
- 实际可并行执行的 `P/M` 资源上限

所以同样是“8 核机器”，不同语言下最佳策略很可能完全不同。

## 8. 应该看哪些指标来判断服务瓶颈

想知道服务应该开多少进程、多少线程，不能靠想象，必须先看指标。

### 8.1 先看系统快照

最常见的方式是通过：

- `top`

看当前机器的整体快照，例如：

- 当前有多少任务在运行
- 当前有多少任务在休眠
- `CPU` 用户态占比
- `CPU` 内核态占比
- `idle`
- `wa`，也就是 `I/O wait`
- 内存和交换分区使用情况

这里要特别注意：

- `top` 看到的是某一时刻的快照

所以它适合快速观察，但不适合直接拿来做长期判断。

### 8.2 平均负载不能只看一次

分析负载时，还要看：

- `load average`

平均负载本质上是：

- 一段时间内可运行任务和不可中断等待任务的平均数量

它必须多次采样、结合时间窗口来理解，不能只看一眼数字就下结论。

尤其是当你发现：

- 平均负载很高
- 同时 `CPU` 的 `I/O wait` 也很高

这往往说明：

- 系统里有大量任务在等待 I/O
- CPU 没能持续做有效计算

常见原因包括：

- 日志打得太频繁
- 数据库读写太频繁
- 网络请求过多
- 下游依赖响应慢

### 8.3 看网络流量

如果怀疑服务瓶颈在网络，可以继续看：

- 网络接口收发字节数
- 包数量
- 错误包
- 丢包

这类指标可以帮助判断：

- 是不是网络通信非常频繁
- 是否存在带宽压力
- 是否存在网络层异常

### 8.4 看磁盘 I/O

如果怀疑瓶颈在磁盘，可以继续看：

- 当前磁盘读写吞吐
- 哪个进程或线程写得最多
- 磁盘利用率
- 文件系统剩余空间

常见排查方式包括：

- 看磁盘读写实时情况
- 看文件系统使用率
- 看更细粒度的磁盘统计信息

在 Linux 里，如果想看更底层的磁盘统计，还可以关注：

- `/proc/diskstats`

### 8.5 做长期监控，而不是只看命令行瞬时结果

线上服务真正有价值的做法通常是：

- 定时收集服务器指标
- 持续记录成日志或监控时序数据
- 回放一段时间内的变化趋势

因为只看某一个时间点，很容易误判。  
而长期监控更适合回答：

- 高峰期瓶颈在哪里
- 压测时资源是怎么变化的
- 优化前后效果如何

## 9. 为什么批量更快

很多 I/O 场景里，批量处理往往会更快。

原因通常包括：

- 可以更充分利用 CPU 缓存
- 可以复用连接
- 可以复用缓冲区
- 可以减少系统调用次数
- 可以减少磁盘或网络上的零碎操作

所以如果 I/O Wait 已经优化得比较困难，往往可以继续考虑：

- 批量写
- 批量读
- 延迟写
- 合并请求
- 减少不必要的网络往返

## 10. 发现瓶颈后，怎么调整线程数和进程数

到这里可以给出一个更实用的判断方式。

### 10.1 如果是计算密集型

如果发现整个过程中的主要瓶颈在 CPU，那么通常应该：

- 优先优化算法
- 优先减少不必要计算
- 让并发数接近 CPU 核数附近

这时如果还盲目增加线程或进程，往往只会：

- 增加上下文切换
- 增加调度开销
- 增加缓存失效

### 10.2 如果是 I/O 密集型

如果发现系统里 `I/O wait` 很高，说明程序花了很多时间在等 I/O。  
这时可以从两个方向考虑：

第一，先优化 I/O 本身：

- 减少日志量
- 减少无效数据库读写
- 合并网络请求
- 使用延迟写、批量写、缓存等手段

第二，再考虑增加线程数或进程数，让更多任务在等待期间互相填补 CPU 空闲。

也就是说：

- **I/O 密集型往往更适合更高的并发执行单元数量**

### 10.3 如果 idle 很高

如果发现：

- `idle` 很高
- CPU 大量闲置
- 但业务吞吐还没达到目标

那么通常可以考虑：

- 增加线程数
- 增加进程数
- 提高并发度

前提是：

- 不能让内存先被打爆
- 不能让下游依赖先被压垮

## 11. 最终怎么定数量

这一节最后的结论其实很务实：

- **没有一个脱离业务和压测环境的固定答案**

无论是：

- 计算密集型
- I/O 密集型
- 多线程模型
- 多进程模型

最终都应该：

- 先做监控
- 再做压测
- 根据不同并发场景下的指标变化来定

判断标准不是“线程开得多不多”，而是：

- 吞吐有没有提升
- 延迟是否可接受
- CPU、内存、磁盘、网络是否健康
- 下游是否被打满
- 是否接近资源耗尽

## 12. 面试里的简洁回答模板

如果面试官问“服务应该开多少个进程、多少个线程”，可以先这样答：

> 要先看服务是计算密集型还是 I/O 密集型。  
> 计算密集型一般让并发度接近 CPU 核数，避免过多调度开销；I/O 密集型因为线程经常等待磁盘、网络、数据库，所以线程数或进程数往往会超过 CPU 核数，用来填补 I/O 等待带来的空闲。  
> 但这不能只靠经验拍板，必须结合监控和压测，看 CPU 使用率、I/O wait、load average、磁盘和网络指标，再决定具体开多少。

## 13. 这一节的核心结论

最后把这一节压缩成几句话：

- 线程数和进程数应该由服务特性决定，而不是固定照着 CPU 核数来配
- 计算密集型更关注 CPU 核数和算法效率
- I/O 密集型更关注 I/O Wait、磁盘、网络和下游依赖
- I/O 多时，线程数或进程数通常会超过 CPU 核数
- 不同语言的运行时模型不同，最佳并发策略也不同
- 最终配置必须依赖监控和压测结果来定
