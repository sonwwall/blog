# 第二十一节：虚拟内存：一个程序最多能使用多少内存？

这一节主要围绕 7 个问题展开：

1. 为什么光靠物理内存不够
2. `Swap` 技术在解决什么问题
3. 为什么 `Swap` 仍然不是理想方案
4. 虚拟内存到底想解决什么
5. 页、页框、页表、`MMU` 分别是什么
6. 多级页表为什么会出现
7. 一个程序最多到底能使用多少内存

## 1. 为什么只靠物理内存不够

随着程序越来越复杂，进程需要的内存会越来越大。  
但机器上的物理内存是有限的，因此操作系统必须思考一个问题：

- 能不能让程序“看起来”拥有很大的内存空间
- 但实际上只把当前真正常用的那部分数据放在内存里

如果做不到这一点，那么系统会很快遇到几个限制：

- 同时能运行的程序数量有限
- 大程序很容易因为内存不足而无法运行
- 程序员必须频繁考虑底层内存是否连续、是否够大

所以问题的核心不是“内存够不够大”，而是：

- **如何更高效地管理有限的物理内存**

## 2. `Swap` 技术在解决什么问题

一个比较早期、也比较直观的思路，就是：

- 允许只有一部分进程驻留在内存中
- 暂时不使用的进程数据先放到磁盘上
- 需要时再把它们重新换回内存

这就是常说的 `Swap` 技术。

可以把它理解成：

- 内存负责放“当前要用”的内容
- 磁盘负责暂存“暂时不用”的内容

这样做的直接收益是：

- 在物理内存有限时，系统仍然可以维持更多进程
- 一个进程也不一定要求它的完整数据始终都在内存里

所以 `Swap` 的本质是：

- **用磁盘空间换内存容量**

## 3. 为什么 `Swap` 仍然不是理想方案

`Swap` 解决了一部分问题，但它很快暴露出两个明显缺点。

### 3.1 会产生碎片问题

如果内存是按整块、连续区域分配给进程的，那么进程不断创建、回收、换入、换出之后，内存里就会留下很多缝隙。

这会导致：

- 可用内存总量可能不少
- 但连续的大块空间不够
- 新进程或扩容后的进程仍然可能分配失败

这就是典型的**外部碎片**问题。

### 3.2 会出现频繁切换问题

如果进程很多，而物理内存又比较小，那么系统会不停在内存和磁盘之间来回交换数据。

这会导致：

- 大量时间花在换入换出上
- CPU 明明没做多少有效计算
- 整体性能急剧下降

这类现象在工程上通常会被理解成：

- 系统把时间浪费在“搬运数据”上，而不是“执行程序”上

所以只靠 `Swap`，最多算是一个过渡方案，并不是现代内存管理的最终答案。

## 4. 虚拟内存到底想解决什么

现代操作系统引入虚拟内存，核心目标通常可以概括成 3 个：

- **隔离**
- **性能**
- **让程序更好写**

### 4.1 隔离

每个进程都拥有自己的地址空间，彼此之间默认互不影响。

这意味着：

- 一个程序看到的是自己的连续地址空间
- 它不需要直接感知其他进程占用了哪些物理内存
- 进程之间的内存访问边界更清晰

### 4.2 性能

程序真正高频访问的数据可以留在内存中，低频使用的数据可以暂存在别处。

也就是说，操作系统希望达到一种效果：

- 热点数据尽量留在更快的层次
- 非热点数据不要长期占着宝贵的物理内存

### 4.3 让程序更好写

程序员写代码时，最好面对的是一个稳定、连续、统一的地址空间，而不是直接操心底层物理内存到底分散在哪些地方。

所以虚拟内存本质上是一种抽象：

- **给程序一个连续的“假想空间”**
- **由操作系统和硬件负责把它映射到真实内存**

## 5. 虚拟内存是怎么做到的

虚拟内存要落地，最常见的方法就是：

- **分页**

它会把虚拟地址空间和物理内存都拆成固定大小的小块。

### 5.1 页和页框

在分页系统里，通常会有两个概念：

- 虚拟内存里的块叫 **页**（`Page`）
- 物理内存里的块叫 **页框**（`Frame`）

通常一页和一个页框大小相同，比如常见的 `4KB`。

这样做的好处是：

- 不再要求一个进程必须占用一整块连续物理内存
- 一个进程的不同页可以分散放在不同的物理页框里

这一下就把“连续分配”的压力大幅降低了。

### 5.2 页表

既然虚拟页可以分散放在不同物理页框里，那么系统就必须记录：

- 某个虚拟页现在对应哪个物理页框

这张映射关系表，就是：

- **页表**

页表里的每一项，不只是简单写一个页框编号，通常还会带一些额外信息，比如：

- 这一页在不在内存里
- 访问权限是什么
- 最近有没有被访问过
- 有没有被修改过
- 是否允许缓存
- 对应的页框编号是多少

所以页表项本质上是：

- **页的映射信息 + 状态信息**

## 6. 地址转换具体是怎么做的

当 CPU 访问一个地址时，它拿到的通常不是物理地址，而是：

- **虚拟地址**

整个转换过程可以先粗略记成 3 步：

1. 先通过虚拟地址计算出页号和页内偏移
2. 再根据页号去查页表，找到对应的页框号
3. 最后把页框号和页内偏移拼起来，形成物理地址

比如页大小是 `4096` 字节，某个虚拟地址是 `100000`，那么：

- 页号 = `100000 / 4096 = 24`
- 偏移 = `100000 % 4096 = 1616`

如果页表里查到：

- 第 `24` 页对应第 `10` 个页框

那么物理地址就可以写成：

- `10 * 4096 + 1616`

这个过程在概念上不复杂，难点在于：

- CPU 执行指令时会频繁访问内存
- 如果每次访存都先去内存里查页表，再去真正读数据，代价会很高

## 7. `MMU` 在这里负责什么

负责地址转换的关键硬件模块，通常叫：

- `MMU`，即内存管理单元 `Memory Management Unit`

它的职责可以简单理解为：

- 接收 CPU 发出的虚拟地址
- 按照页表规则把虚拟地址翻译成物理地址
- 再去访问真正的物理内存

所以从执行路径上看，大致是：

- CPU 给出虚拟地址
- `MMU` 完成地址翻译
- 最终访问到物理内存

不同 CPU 架构上的 `MMU` 实现会有差异，所以虚拟内存这块天然会带一些平台相关性。

## 8. 为什么页表本身也会很大

如果一个进程的虚拟地址空间很大，而页大小又比较小，那么页的数量会非常多。

页一多，页表就会跟着变大。

举个直观例子：

- 如果页大小是 `4KB`
- 一个较大的地址空间会被拆成海量页
- 那么每一页都要有一项页表项

这时就会出现一个新问题：

- **页表自己会占用不少内存**

如果仍然用“一整张线性大表”去表示，很多页表项其实对应的是根本没用到的虚拟空间，这会造成明显浪费。

## 9. 多级页表为什么会出现

为了解决页表过大的问题，操作系统通常不会只用一级页表，而是改成：

- **多级页表**

它的核心思想是：

- 不一次性把整个大页表完整建出来
- 而是把页表继续拆分成多层结构
- 哪一段地址空间真的被用到了，再按需分配对应层级的页表

这样做的好处是：

- 稀疏地址空间不会为“没用到的部分”付出完整页表成本
- 对空间利用率更友好

可以把它理解成一个递归拆分过程：

- 虚拟地址先拆出一级编号
- 再拆出二级编号
- 最后再配合页内偏移完成定位

层级增加后：

- 空间利用率通常更高
- 但查询链路也会更长
- 因此会带来一定额外开销

所以这是一个典型的空间换时间、时间换空间的权衡。

## 10. 一个程序最多能使用多少内存

这个问题本质上问的是：

- **一个进程最多能拥有多大的虚拟地址空间**

如果只从最理想的数学上限看：

- `32` 位机器最多可寻址 `2^32` 字节，也就是 `4GB`
- `64` 位机器最多可寻址 `2^64` 字节

但在真实系统里，情况不会这么简单。

原因是：

- `2^64` 这个数太大了，远超大多数机器真正需要的规模
- 处理器、操作系统、内核设计通常不会把所有 `64` 位都完全拿来做用户空间寻址
- 一部分地址范围还要留给内核空间、保留区、硬件映射等用途

所以实际看到的情况通常是：

- `32` 位进程常见上限接近 `4GB`，但通常还要和内核空间分割
- `64` 位进程理论空间极大，实际往往是几十到几百 `TB`，甚至更大规模
- 从“面试级理解”看，可以把它记成：**64 位程序的可用虚拟空间通常已经大到远超真实物理内存**

换句话说：

- 一个程序“最多能用多少内存”，往往先受虚拟地址空间限制
- 但真正能不能稳定使用，还会继续受物理内存、页表开销、系统策略、资源限制等因素影响

## 11. 一个更容易记住的总结

可以把这一节压缩成下面几句话：

- `Swap` 让系统能把暂时不用的数据放到磁盘上
- 但它会带来碎片和频繁切换等问题
- 虚拟内存给每个进程提供了独立、连续的地址空间
- 分页把虚拟页映射到离散的物理页框上
- 页表负责记录页到页框的映射以及各种状态位
- `MMU` 负责把虚拟地址翻译成物理地址
- 多级页表是为了解决“大地址空间下页表太浪费”的问题
- 程序最多能使用多少内存，本质上取决于可用虚拟地址空间和系统实现

## 12. 最后补一个问题：可不可以用哈希表直接把页号映射到页框号

可以，但不能简单理解成：

- “把普通页表全都换成语言层面的哈希表，就更好了”

更准确地说是：

- **有些系统确实会使用哈希页表 `Hashed Page Table` 这类结构**
- **但主流通用操作系统和硬件体系里，更常见的仍然是分层页表**

原因主要有 4 个：

### 12.1 当然可以表达映射关系

从数据结构角度说：

- 页号 -> 页框号

本来就是一个键值映射，因此用哈希表表达在逻辑上完全可行。

### 12.2 但硬件更偏爱规则化结构

地址翻译是高频操作，发生在几乎每次访存里。  
这类操作非常依赖硬件支持，而硬件通常更喜欢：

- 结构固定
- 访问路径可预测
- 便于和 `TLB`、页表遍历逻辑协同

分层页表在这方面更容易标准化，也更容易被 CPU 直接支持。

### 12.3 哈希会带来冲突和额外处理

如果用哈希表，就要面对：

- 哈希冲突
- 桶管理
- 链表或开放寻址
- 负载因子变化

这些问题放到普通软件里不算大事，但放到超高频的地址翻译路径上，就会让硬件设计和时延控制都更麻烦。

### 12.4 它更适合某些特定场景

哈希页表更适合：

- 地址空间非常大
- 虚拟页分布非常稀疏
- 希望避免巨大的线性页表或多级页表开销

所以结论可以记成：

- **逻辑上可以**
- **工程上也确实存在这种实现**
- **但在主流体系里，通常不是最通用、最主流的方案**

如果面试里被问到，你可以直接回答：

> 可以，页号到页框号本质上就是映射关系，理论上可以用哈希表做，实际也有哈希页表这类设计。  
> 但主流系统更常见的是多级页表，因为它更适合硬件高频地址翻译，也更容易和 `MMU`、`TLB` 协同工作。
