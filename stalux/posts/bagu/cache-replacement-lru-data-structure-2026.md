# 第二十六节：缓存置换算法：LRU 用什么数据结构实现更合理？

这一节主要围绕 8 个问题展开：

1. 缓存置换算法解决什么问题
2. 好的缓存置换算法希望达到什么目标
3. 随机、`FIFO`、`FILO` 为什么不够好
4. `NRU` 和第二次机会算法是什么
5. `LRU` 为什么比 `NRU` 考虑得更多
6. `LRU` 用什么数据结构实现更合理
7. 为什么 CPU 缓存里常用近似 `LRU`
8. `LFU`、老化算法和 `LFUDA` 在解决什么问题

## 1. 缓存置换算法解决什么问题

缓存容量通常远小于后端存储容量。

比如：

- CPU 缓存小于内存
- `TLB` 小于页表
- 内存小于磁盘
- `Redis` 缓存小于数据库

当缓存满了，新条目又要写入时，就必须决定：

- **哪个旧条目应该被替换出去**

这就是缓存置换算法要解决的问题。

它不只出现在操作系统里。  
CPU 缓存、页缓存、页面置换、数据库缓冲池、应用层缓存都需要类似策略。

可以把它类比成：

- CPU 缓存每次写入一个新缓存行，相当于一个旧缓存行被覆盖
- 数据库要决定哪些数据留在内存里
- 应用开发要决定哪些数据继续留在 `Redis` 中

所以缓存置换的本质是：

- **在有限缓存空间里，尽量保留未来更可能被访问的数据**

## 2. 好的缓存置换算法想达到什么目标

理想情况下，缓存置换算法希望做到：

- 每次淘汰未来最不会被使用的数据
- 尽量提高缓存命中率
- 尽量降低访问延迟
- 自身维护成本不能太高

如果用一个简化公式表示缓存平均访问时间，可以写成：

```text
平均访问时间 = L + M * T
```

其中：

- `L` 表示访问缓存本身的时间
- `M` 表示缓存未命中的概率
- `T` 表示缓存未命中后，从后端获取数据的平均时间

这个公式想表达的是：

- 缓存本身要足够快
- 未命中概率要足够低
- 未命中后的代价越大，缓存命中率就越重要

所以置换算法的核心目标是：

- **降低 `M`，也就是降低缓存未命中概率**

但算法不能只追求命中率。  
如果为了找一个“最该淘汰”的条目，每次都要遍历整个缓存，那么缓存本身的维护成本也会变高。

因此真正的工程权衡是：

- **命中率**
- **维护开销**
- **实现复杂度**
- **硬件或软件场景是否适合**

## 3. 随机、`FIFO`、`FILO`

### 3.1 随机置换

随机置换很直观：

- 新条目写入时，随机淘汰一个旧条目

它的优点是：

- 实现极其简单
- 不需要维护访问历史
- 开销很低

但缺点也明显：

- 可能刚好淘汰热点数据
- 命中率不稳定
- 不适合需要较高命中率的场景

随机置换更像一个低成本兜底方案，而不是追求高命中率的精细策略。

### 3.2 `FIFO`

`FIFO` 是 `First In First Out`，先进先出。

它的规则是：

- 最早进入缓存的数据最先被淘汰

这个策略实现也很简单，只需要维护进入缓存的顺序。

但问题是：

- 进入时间早，不代表现在不重要
- 进入时间晚，也不代表未来更重要

比如一个电商首页，如果每次都把停留时间最长的产品下线，就可能忽略销量、热度、好评率等因素。  
放到缓存里也类似：一个老缓存条目可能仍然是高频热点，简单按进入时间淘汰会误伤它。

### 3.3 `FILO`

`FILO` 是 `First In Last Out`，先进后出。

它的效果接近：

- 新进来的数据更容易先被淘汰

在普通缓存置换场景下，`FILO` 和随机一样，通常没有很强的实际意义。  
它既没有很好利用最近访问情况，也没有很好利用访问频率。

所以这三类朴素算法的问题可以总结成：

- **规则简单**
- **维护成本低**
- **但没有充分利用访问历史**

## 4. `NRU`：最近未使用

`NRU` 是 `Not Recently Used`，最近未使用。

它的基本思想是：

- 优先把最近没有使用过的数据置换出去

相比 `FIFO`，`NRU` 开始利用访问历史。  
它不再只看“谁先进来”，而是看“最近有没有被访问过”。

在页面置换场景中，硬件和操作系统通常会在页表项里维护一些状态位，比如：

- `Absent`：页是否在内存中
- `Protection`：访问权限
- `Reference`：最近是否被访问过
- `Dirty`：是否被修改过
- `Caching`：是否允许缓存
- `Frame Number`：对应的物理页框号

其中 `Reference` 位和 `Dirty` 位对页面置换尤其重要。

### 4.1 `Reference` 位

`Reference` 位表示：

- 这个页面最近是否被访问过

如果页面被读或写，硬件可以把 `Reference` 位设置为 `1`。  
操作系统隔一段时间把它清零，就可以近似知道哪些页“最近被用过”。

### 4.2 `Dirty` 位

`Dirty` 位表示：

- 这个页面是否被修改过

如果一个页面没有被修改，淘汰时可以直接丢弃，因为磁盘上还有原始内容。  
如果一个页面被修改过，淘汰前通常要写回磁盘，成本更高。

因此，在选择淘汰页面时，操作系统通常更愿意先淘汰：

- 最近没被访问
- 并且没有被修改

### 4.3 `NRU` 的分类思想

`NRU` 可以把页面按 `Reference` 和 `Dirty` 分成几类：

| 类别 | `Reference` | `Dirty` | 含义 | 淘汰优先级 |
| --- | --- | --- | --- | --- |
| 0 | 0 | 0 | 最近没访问，也没修改 | 最高 |
| 1 | 0 | 1 | 最近没访问，但修改过 | 较高 |
| 2 | 1 | 0 | 最近访问过，没修改 | 较低 |
| 3 | 1 | 1 | 最近访问过，也修改过 | 最低 |

这样做的好处是：

- 简单
- 有效
- 可以利用硬件提供的访问位和脏位

它的问题是：

- 只知道“最近有没有被访问”
- 不知道“访问了多少次”
- 也不知道更精细的访问顺序

所以 `NRU` 是一个很实用的近似算法，但它不是完整的 `LRU`。

## 5. 第二次机会算法

第二次机会算法可以理解成：

- 用一个环形链表改进 `FIFO`

它通常维护一个指针，指向下一个候选淘汰页。  
当需要淘汰页面时：

1. 查看当前页面的 `Reference` 位
2. 如果 `Reference = 0`，说明最近没用过，可以淘汰
3. 如果 `Reference = 1`，说明最近用过，把它清零
4. 指针继续往后走，给这个页面第二次机会

这就是“第二次机会”的含义：

- 如果一个页面最近被访问过，就先不淘汰它
- 但把它的访问位清掉
- 如果下一轮还没有再次被访问，就可能被淘汰

它的常见实现形式也叫：

- `Clock` 算法

因为所有页面像时钟一样围成一个环，指针像表针一样向前移动。

第二次机会算法的优点是：

- 比纯 `FIFO` 更合理
- 实现简单
- 不需要维护完整访问顺序
- 适合操作系统页面置换

它的缺点是：

- 仍然只是近似
- 不能精确表达“最近最少使用”
- 对访问频率的表达也比较弱

## 6. `LRU`：最近最少使用

`LRU` 是 `Least Recently Used`，最近最少使用。

它相比 `NRU` 多考虑了一层：

- 不只是看最近有没有被访问
- 还要维护谁更近被访问，谁更久没被访问

它背后的假设是：

- 最近被访问的数据，接下来更可能继续被访问
- 很久没被访问的数据，未来被访问的概率更低

这个假设来自程序访问的局部性原理。

常见局部性包括：

- 时间局部性：刚访问过的数据，短时间内可能再次访问
- 空间局部性：访问某个地址后，附近地址也可能被访问

`LRU` 主要利用的是时间局部性。

## 7. `LRU` 用什么数据结构实现更合理

如果在软件里实现 `LRU`，最经典、最合理的结构是：

- **哈希表 + 双向链表**

### 7.1 为什么不能只用数组

用数组当然可以实现 `LRU`。

比如：

- 数组头部表示最近使用
- 数组尾部表示最久未使用
- 每次访问一个元素，就把它移动到头部
- 缓存满了，就淘汰尾部元素

但问题是：

- 查找某个 `key` 需要遍历数组
- 把中间元素移动到头部也要搬移元素
- 时间复杂度通常是 `O(n)`

缓存容量小的时候还可以接受。  
缓存容量一大，开销就很明显。

所以数组更适合：

- 容量很小
- 实现简单优先
- 对性能要求不高的场景

### 7.2 为什么要用双向链表

双向链表适合维护访问顺序。

常见约定是：

- 链表头部表示最近使用
- 链表尾部表示最久未使用

每次访问一个缓存条目时：

1. 从链表当前位置摘下来
2. 移动到链表头部

当缓存满了时：

- 直接淘汰链表尾部节点

双向链表的好处是：

- 已知节点时，删除是 `O(1)`
- 插入头部是 `O(1)`
- 淘汰尾部是 `O(1)`

但它还缺一个能力：

- 根据 `key` 快速找到节点

这就需要哈希表。

### 7.3 为什么还要哈希表

哈希表负责查询能力：

```text
key -> 双向链表节点
```

这样查询一个缓存项时：

1. 先用哈希表 `O(1)` 找到节点
2. 如果存在，就把节点移动到链表头部
3. 如果不存在，就从后端加载数据
4. 新数据插入链表头部
5. 如果容量超限，就删除链表尾部节点，并同步删除哈希表里的映射

因此软件 `LRU` 的核心结构是：

```text
HashMap + Doubly Linked List
```

可以把它记成：

- 哈希表解决查询
- 双向链表解决顺序
- 链表头表示最新
- 链表尾表示最旧

### 7.4 `get` 和 `put` 如何工作

`get(key)`：

1. 查哈希表
2. 如果不存在，返回未命中
3. 如果存在，拿到链表节点
4. 把节点移动到链表头部
5. 返回节点里的值

`put(key, value)`：

1. 如果 `key` 已存在，更新值，并移动到链表头部
2. 如果 `key` 不存在，新建节点插入链表头部
3. 把 `key -> node` 写入哈希表
4. 如果超过容量，删除链表尾部节点
5. 删除尾部节点对应的哈希表项

这样 `get` 和 `put` 都可以做到均摊 `O(1)`。

这就是为什么面试里问：

> `LRU` 用什么数据结构实现更合理？

最标准的回答通常是：

> 用哈希表加双向链表。哈希表提供 `O(1)` 查询，双向链表维护访问顺序。每次访问或更新节点时，把节点移动到链表头部；缓存满时淘汰链表尾部节点。

## 8. `LRU` 在硬件里为什么不一定精确实现

软件里用哈希表加双向链表实现 `LRU` 很常见。  
但在 CPU 缓存、`TLB` 这类硬件场景里，精确 `LRU` 不一定划算。

原因是：

- 硬件访问路径要求极低延迟
- 每次访问都维护完整顺序，成本很高
- 路数越多，精确记录顺序越复杂
- 硬件面积和功耗也要考虑

所以 CPU 缓存里常见的是：

- 近似 `LRU`
- 伪 `LRU`
- 随机或混合策略
- 每组内部维护少量状态位

尤其是多路组相联缓存中，置换只发生在一个组内。  
比如 `8-way` 组相联缓存，某个地址先定位到一个组，然后只需要在这个组的 `8` 个候选缓存行里选择一个替换。

这时要实现 `LRU`，有几种思路：

- 精确维护这 `8` 路的使用顺序
- 给每一路维护计数器或时间戳
- 使用树形伪 `LRU`
- 使用类似 `Clock` 的近似策略

如果路数较小，精确 `LRU` 还能接受。  
如果路数较大，近似 `LRU` 往往更现实。

所以要区分：

- **应用层缓存：哈希表 + 双向链表很常见**
- **CPU 缓存 / TLB：常用硬件友好的近似 `LRU`**

## 9. `LFU`：最少使用

`LFU` 是 `Least Frequently Used`，最少使用。

它的思路是：

- 根据使用次数决定淘汰谁
- 使用次数最少的数据优先被替换

相比 `LRU`：

- `LRU` 关注最近一次使用时间
- `LFU` 关注累计使用次数

比如一个缓存项在过去被访问了 `1000` 次，另一个只访问了 `2` 次。  
如果只看使用频率，`LFU` 会更愿意保留前者。

但 `LFU` 有一个典型问题：

- 它不会自然忘记历史

如果某个数据曾经很热，计数很高，但后来已经不再被访问，它仍然可能长期留在缓存中。  
这会导致旧热点占住位置，新热点进不来。

所以 `LFU` 需要配合衰减或老化机制。

## 10. 老化算法

老化算法 `Aging` 试图解决：

- 如何既考虑访问次数，又让旧访问逐渐失效

一种常见做法是：

- 为每个页面维护一个计数器 `A`
- 每隔一个时间片，把 `A` 右移一位
- 如果这个时间片内页面被访问过，就把访问位 `R` 放到 `A` 的最高位

例如 `A` 初始是：

```text
00000000
```

如果 5 个 Tick 中，访问位 `R` 到来的序列是：

```text
11100
```

那么每次右移并把 `R` 放到最高位后，可能得到：

```text
1. 10000000
2. 11000000
3. 11100000
4. 01110000
5. 00111000
```

这样，越近的访问越靠近高位，权重越大；越久远的访问会不断右移，影响逐渐变小。

所以老化算法的好处是：

- 保留了一定访问频率信息
- 又不会让很久以前的访问永久有效
- 可以近似表达“最近一段时间内的使用情况”

页面置换时，可以优先淘汰 `A` 值较小的页面。

## 11. `LFUDA`

`LFUDA` 可以理解成：

- 带动态老化的 `LFU`

它试图缓解普通 `LFU` 的历史包袱问题。

普通 `LFU` 只看累计次数，容易让历史热点长期霸占缓存。  
`LFUDA` 会引入一个全局老化因子，让旧缓存项的优势逐渐降低。

一种理解方式是：

- 每个缓存项有一个优先级值
- 优先级和访问频率有关
- 系统淘汰优先级最低的缓存项
- 每次淘汰后，根据被淘汰项更新全局老化值

这样可以让缓存逐步适应新的访问模式。

它适合讨论：

- 使用频率很重要
- 访问模式会变化
- 不希望历史热点永远留在缓存里

但它也更复杂，不像 `LRU` 那样容易用一个哈希表加双向链表讲清楚。

## 12. 到底要不要采用 `LRU`

是否采用 `LRU`，要看具体场景。

可以从两个角度判断：

- 性能要求是什么
- 最终结果能不能达到期望命中率和延迟

如果是应用层缓存，`LRU` 很常见。  
因为它能用相对简单的数据结构实现，并且能很好利用时间局部性。

如果是 CPU 缓存或 `TLB`，就要考虑硬件实现成本。  
精确 `LRU` 在高性能硬件里可能过于昂贵，因此常用近似算法。

如果访问模式更接近“历史高频更重要”，可以考虑 `LFU` 或带老化的 `LFU`。  
如果只需要简单低成本策略，也可以考虑随机、`FIFO`、`Clock`。

所以没有一个算法在所有场景下都是最优的。  
置换算法本质上是在做权衡：

- 命中率
- 维护成本
- 实现复杂度
- 对访问模式的适应能力

## 13. 面试里怎么回答

如果面试官问：

> `LRU` 用什么数据结构实现更合理？

可以直接回答：

> 在软件缓存里，`LRU` 通常用哈希表加双向链表实现。哈希表负责根据 `key` 快速找到缓存节点，双向链表负责维护最近使用顺序。每次访问节点时，把它移动到链表头部；插入新节点也放到头部；缓存满时淘汰链表尾部节点。这样 `get` 和 `put` 都可以做到均摊 `O(1)`。

然后可以补充硬件场景：

> 但在 CPU 缓存或 `TLB` 这种硬件缓存里，不一定会精确实现 `LRU`。因为每次访问都维护完整顺序会增加硬件复杂度、面积、功耗和延迟。多路组相联缓存里通常只在一个组内选择替换项，可以使用精确 `LRU`、伪 `LRU`、`Clock` 或其他近似策略。

最后再补一层对比：

> `LRU` 关注最近一次访问时间，适合利用时间局部性；`LFU` 关注访问次数，但容易保留过期热点，所以常常需要老化机制。`NRU` 和第二次机会算法更简单，适合页面置换中利用访问位做近似判断。

## 14. 这一节先记住的点

- 缓存置换算法决定缓存满时淘汰哪个旧条目
- 好的置换算法希望降低未命中率，但维护成本不能太高
- 随机、`FIFO`、`FILO` 简单，但利用访问历史太少
- `NRU` 利用访问位，优先淘汰最近没用过的页面
- 第二次机会算法用环形链表和访问位改进 `FIFO`
- `LRU` 维护最近使用顺序，利用时间局部性
- 软件 `LRU` 常用哈希表加双向链表
- 哈希表负责 `O(1)` 查询，双向链表负责 `O(1)` 移动和淘汰
- CPU 缓存和 `TLB` 中精确 `LRU` 成本较高，常用近似 `LRU`
- `LFU` 看使用次数，但需要处理历史热点问题
- 老化算法通过右移计数器，让旧访问逐渐失效
- 选择置换算法时，要结合命中率、延迟、维护成本和访问模式判断
