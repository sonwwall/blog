# 第十七节：线程的调度：线程调度都有哪些方法？

这一节主要围绕 6 个问题展开：

1. 最朴素的线程调度方法是什么
2. 为什么只用先到先服务会有问题
3. 抢占式调度和非抢占式调度分别解决什么问题
4. 优先级队列为什么适合表达“紧急任务先做”
5. 最短作业优先为什么难以直接落地
6. 分级队列为什么是工程上更常见的做法

## 1. 先从最朴素的调度方式开始：先到先服务

最容易想到的调度模型，就是**先到先服务**。

它的规则非常简单：

- 谁先进入队列，谁先执行
- 当前任务没有执行完，后面的任务就继续等待
- 队列整体呈现出一种先进先出（FIFO）的性质

这种方式有两个很明显的优点：

- **公平性直观**：大家按到达顺序排队，规则简单，容易理解
- **吞吐量高**：任务之间没有频繁切换，额外调度开销很小

所以从“实现成本”和“系统开销”的角度看，先到先服务确实是最朴素的一种方案。

## 2. 先到先服务为什么不够好

问题在于，用户通常不只关心“规则是不是简单”，更关心“自己到底要等多久”。

举个很典型的场景：

- 如果前面是一个执行 10 分钟的任务，用户等 10 分钟，也许还能接受
- 但如果前面是一个要执行 1 天的大任务，而你自己的任务只要 1 分钟，那等待体验就会非常差

这说明一个核心问题：

- **先到先服务能保证顺序上的朴素公平**
- 但**不能很好地降低平均等待时间**

也正因为如此，操作系统通常不会只满足于“排队排得整齐”，而会进一步思考：

- 能不能让紧急任务先做
- 能不能让短任务更快完成
- 能不能避免一个长任务长期霸占 CPU

## 3. 短作业优先：希望让短任务先完成

为了降低平均等待时间，一个很自然的思路是**短作业优先**。

它的出发点是：

- 短任务先做完，系统可以更快释放资源
- 用户也更容易感知到“响应快”

但这个思路马上会遇到几个现实问题：

1. 紧急任务如何插队，比如一个临时必须马上处理的任务
2. 等了太久的任务怎么办，继续等下去可能造成饥饿
3. 如果已经开始执行一个大任务，后面才来了一个只要 1 分钟的小任务，该怎么处理

更关键的是，**最短作业优先依赖于“预估执行时间”**。

而在真实系统里：

- 线程到底会跑多久，很多时候事先并不知道
- CPU 密集型和 I/O 密集型任务还会动态变化
- 同一个任务在不同负载下，执行时间也可能完全不同

所以“让最短任务优先”这个目标虽然合理，但它很难被精确实现。

## 4. 优先级调度：把“谁更重要”显式表达出来

另一种更工程化的做法，是给每个任务一个**优先级**。

调度器每次都从就绪任务中挑选优先级最高的那个执行。

这样做的好处是：

- 可以显式表达“紧急任务先处理”
- 比单纯按照到达顺序更灵活
- 比只看执行时间更容易落地

如果从数据结构上实现，优先级调度通常可以借助**优先级队列**。

它的核心思想是：

- 队列中的每个元素都带有优先级
- 每次不再线性扫描所有任务，而是尽量快速找到当前优先级最高的任务

常见实现会用堆来维护优先级队列，这样可以更高效地取出“当前最该执行的任务”。

## 5. 优先级怎么定义

优先级本身不是固定不变的，它往往是一个综合指标。

一个常见思路是同时考虑：

- **等待时间 W**
- **预估执行时间 P**

于是可以构造出类似下面这样的倾向：

- 等得越久，优先级越应该提高
- 预计执行时间越短，优先级也越应该更高

你的笔记里给出的一个典型表达是：

- **优先级 = W / P**

这类公式背后的本质不是死记一个数学形式，而是理解调度器在平衡两件事：

- 不要让短任务等太久
- 也不要让老任务一直饿死

## 6. 抢占：解决“一个任务长期霸占 CPU”的问题

即使有了优先级队列，如果一个任务一旦开始执行就必须跑到结束，问题仍然存在。

因为这意味着：

- 后面来的高优先级任务无法及时插入
- 短任务也可能被一个长任务拖住

因此操作系统通常还会引入**抢占**机制。

它的核心思想是：

- 把 CPU 执行能力切成一个个时间片
- 每个任务先运行一个时间片
- 时间片用完后，调度器重新决定下一个该运行谁

这样做之后，线程调度就从“谁先来谁一直跑”变成了“大家轮流拿到 CPU，但每轮谁先拿到由调度器决定”。

## 7. 抢占和优先级结合后，形成基本线程调度模型

现代线程调度一般不是单独使用某一种策略，而是把几种思想组合起来：

- 用优先级表达任务的重要程度
- 用时间片实现抢占
- 用等待时间修正优先级，避免低优先级任务永远拿不到 CPU

于是，一个比较基础的模型就出现了：

- 先维护一个按优先级组织的就绪队列
- 每次挑选优先级最高的任务运行一个时间片
- 时间片结束后，根据任务行为重新排队

这个模型已经比“纯先到先服务”更接近真实操作系统。

## 8. 但最短作业优先仍然没有被真正解决

问题在于，如果想实现“最短作业优先的抢占版本”，调度器仍然需要知道：

- 每个线程后面还要执行多久

而这件事通常是不可预知的。

所以真实系统不会直接依赖一个完美的“剩余执行时间”模型，而是采用一种更可操作的折中方案：

- 不去精确预测每个线程到底还剩多久
- 而是通过历史行为，把线程逐步分流到不同优先级队列

## 9. 分级队列：工程上更常见的折中实现

分级队列的核心思路，是把线程放进**不同优先级的多个队列**里。

然后让不同队列采用不同的调度策略。

一个很常见的设计是：

- **高优先级队列**：更强调响应速度，可以采用非抢占或极短时间片，优先处理紧急任务
- **中优先级队列**：采用较短时间片，兼顾吞吐和交互体验
- **低优先级队列**：采用更长时间片，主要容纳长任务或后台任务

这样设计的好处是：

- 短任务通常会在更高优先级队列里更快完成
- 长任务如果持续占用 CPU，会逐渐下沉到更低优先级队列
- 系统既保留了抢占能力，也保留了优先级区分

换句话说，它不是精确地实现“最短作业优先”，而是**近似地让短任务更快完成、长任务逐渐下调优先级**。

## 10. 为什么分级队列有效

因为它绕开了一个最难的问题：

- 操作系统无法准确预判每个线程的总执行时间

于是它改成观察“线程已经表现出来的行为”：

- 如果一个线程很快就结束，它通常会停留在高优先级队列中
- 如果一个线程反复用完整个时间片，说明它更像长任务，优先级就可以逐步下调

这样一来，系统不需要未卜先知，也能逐渐把任务分层：

- 交互型、短任务，更容易留在高优先级层
- CPU 密集型、长任务，会逐渐沉到低优先级层

这就是分级反馈队列背后的核心思想。

## 11. 这一节怎么串起来理解

把这一节串起来，其实就是一条不断修正的思路：

1. 先到先服务最简单，实现成本低，公平也直观
2. 但它无法优化平均等待时间，长任务会严重拖慢短任务
3. 短作业优先可以改善等待时间，但执行时间通常不可准确预测
4. 优先级调度能表达“谁更重要”
5. 抢占机制能防止线程长期霸占 CPU
6. 分级队列把优先级和抢占结合起来，成为更实用的工程方案

所以当别人问“线程调度都有哪些方法”时，不要只背名词，而是要知道它们背后的演化关系：

- 从先到先服务出发
- 为了更好的响应时间，引入短作业优先和优先级
- 为了避免长时间霸占，引入抢占
- 为了在未知执行时间下仍然逼近最优效果，引入分级反馈队列

## 12. 最后补一个面试延伸题

如果让你**使用 Go 语言模拟一个分级队列调度模型**，你会怎么设计：

- 任务结构需要包含哪些字段
- 多级队列如何表示
- 时间片轮转如何推进
- 任务在什么条件下升级、降级或重新入队
- 如何统计平均等待时间、响应时间和吞吐量

这个题如果放在面试里，核心不是让你真的手写一个完整调度器，而是看你能不能把**分级反馈队列**拆成几个可以落地的数据结构和流程。

可以按下面这个思路来回答。

## 13. 如果用 Go 模拟，先定义任务结构

一个任务至少要包含下面这些信息：

- `ID`：任务标识
- `ArrivalTime`：到达时间
- `BurstTime`：总执行时间
- `RemainingTime`：剩余执行时间
- `QueueLevel`：当前所在队列级别
- `FirstRunTime`：第一次被调度的时间，用来统计响应时间
- `FinishTime`：结束时间
- `WaitTime`：累计等待时间

为什么要这些字段：

- 没有 `ArrivalTime`，就无法模拟任务何时进入系统
- 没有 `RemainingTime`，就无法做抢占和重新入队
- 没有 `QueueLevel`，就无法表示“线程被降级”
- 没有 `FirstRunTime` 和 `FinishTime`，就没法统计调度效果

用 Go 表示，大概可以写成：

```go
type Task struct {
	ID            int
	ArrivalTime   int
	BurstTime     int
	RemainingTime int
	QueueLevel    int
	FirstRunTime  int
	FinishTime    int
	Started       bool
}
```

## 14. 多级队列怎么表示

最简单的办法，是直接用一个二维切片表示多个就绪队列：

```go
queues := [][]*Task{
	{}, // Q0: 最高优先级
	{}, // Q1
	{}, // Q2: 最低优先级
}
```

然后再单独维护每一级队列的时间片：

```go
timeSlices := []int{1, 2, 4}
```

这就表达了两个意思：

- 越高优先级，时间片越短，响应越快
- 越低优先级，时间片越长，更适合长任务

如果再细一点，还可以约定：

- 最高优先级队列优先被扫描
- 只要高优先级队列非空，就不会去执行低优先级队列

这就符合分级队列“高优先级优先”的基本思想。

## 15. 调度流程怎么推进

可以把整个模拟器看成一个按时间推进的循环。

每一轮主要做 4 件事：

1. 把当前时刻到达的新任务放入最高优先级队列
2. 从高到低找到第一个非空队列
3. 取出队首任务，运行一个时间片
4. 根据运行结果决定任务是完成、降级，还是重新入队

伪代码逻辑大概是这样：

```text
for 还有任务没完成:
    先把当前时间到达的任务加入 Q0
    从 Q0 到 Qn 找第一个非空队列
    取出一个任务执行
    执行时长 = min(时间片, 剩余时间)
    时间向前推进
    如果任务完成:
        记录完成时间
    否则:
        如果没到最低队列，降到下一队列
        否则回到当前队列尾部
```

这其实就是最经典的 MLFQ 简化模型。

## 16. 任务什么时候升级、降级、重新入队

这部分才是这个题的重点。

一个常见的简化规则是：

- **新任务**：统一先进入最高优先级队列
- **时间片用完且没执行完**：说明更像长任务，降到下一层
- **已经在最低层还没执行完**：不再降级，回到本层队尾
- **执行过程中提前结束**：直接出队，记录完成时间

如果想再模拟得更真实一点，还可以加一个“老化”机制：

- 某个任务等待太久，就把它提升一级

这样可以避免低优先级任务长期饥饿。

所以从面试表达上，你可以直接说：

- 降级是为了让长期占用 CPU 的任务逐渐下沉
- 升级是为了防止饥饿
- 新任务进高优队列，是为了优先保证交互响应

## 17. 一个简化版 Go 模型可以怎么写

下面给一个可以说明思路的简化版代码。

```go
package main

import "fmt"

type Task struct {
	ID            int
	ArrivalTime   int
	BurstTime     int
	RemainingTime int
	QueueLevel    int
	FirstRunTime  int
	FinishTime    int
	Started       bool
}

func main() {
	tasks := []*Task{
		{ID: 1, ArrivalTime: 0, BurstTime: 8, RemainingTime: 8},
		{ID: 2, ArrivalTime: 1, BurstTime: 4, RemainingTime: 4},
		{ID: 3, ArrivalTime: 2, BurstTime: 1, RemainingTime: 1},
	}

	timeSlices := []int{1, 2, 4}
	queues := [][]*Task{{}, {}, {}}

	currentTime := 0
	finished := 0

	for finished < len(tasks) {
		for _, task := range tasks {
			if task.ArrivalTime == currentTime {
				task.QueueLevel = 0
				queues[0] = append(queues[0], task)
			}
		}

		level := -1
		for i := 0; i < len(queues); i++ {
			if len(queues[i]) > 0 {
				level = i
				break
			}
		}

		if level == -1 {
			currentTime++
			continue
		}

		task := queues[level][0]
		queues[level] = queues[level][1:]

		if !task.Started {
			task.Started = true
			task.FirstRunTime = currentTime
		}

		runTime := timeSlices[level]
		if task.RemainingTime < runTime {
			runTime = task.RemainingTime
		}

		task.RemainingTime -= runTime
		currentTime += runTime

		for _, t := range tasks {
			if t.ArrivalTime > currentTime-runTime && t.ArrivalTime <= currentTime {
				t.QueueLevel = 0
				queues[0] = append(queues[0], t)
			}
		}

		if task.RemainingTime == 0 {
			task.FinishTime = currentTime
			finished++
		} else {
			if level < len(queues)-1 {
				task.QueueLevel = level + 1
			}
			queues[task.QueueLevel] = append(queues[task.QueueLevel], task)
		}
	}

	var totalTurnaround, totalResponse int
	for _, task := range tasks {
		turnaround := task.FinishTime - task.ArrivalTime
		response := task.FirstRunTime - task.ArrivalTime
		totalTurnaround += turnaround
		totalResponse += response
		fmt.Printf("task=%d turnaround=%d response=%d\n", task.ID, turnaround, response)
	}

	fmt.Printf("avg turnaround=%.2f\n", float64(totalTurnaround)/float64(len(tasks)))
	fmt.Printf("avg response=%.2f\n", float64(totalResponse)/float64(len(tasks)))
}
```

## 18. 这段代码体现了什么

这段代码虽然简化，但已经体现了分级反馈队列的几个关键点：

- 新任务优先进入高优先级队列
- 高优先级队列先执行
- 每一层使用不同时间片
- 任务如果总是跑不完，会逐渐下沉
- 短任务往往能在高优先级层更快结束

这就达到了“近似最短作业优先”的效果。

## 19. 如果面试官继续追问，你可以怎么补

如果面试官问“这个模型还缺什么”，可以继续补下面几点：

- 现在的实现没有真正做“老化”，可以增加等待阈值，超过阈值就升级
- 现在默认同级队列内部是 FIFO，也可以改成轮转调度
- 现在是单核 CPU 模型，多核场景可以给每个核维护本地运行队列
- 现在没有区分 I/O 型任务和 CPU 型任务，真实系统会根据任务行为动态调整优先级

这时候你的回答就会从“会背概念”，变成“真的知道怎么落地”。

## 20. 这个题最后可以怎么总结

所以这个题最好的回答方式不是一上来写代码，而是先说清楚：

- 用 `Task` 结构表示任务状态
- 用多个队列表示不同优先级
- 用不同时间片体现不同层级的调度策略
- 用“新任务进高优队列、长任务逐渐降级、老任务等待过久可升级”来模拟分级反馈

最后再补一句：

- **Go 语言只是实现载体，核心是把调度策略抽象成数据结构和状态流转**

这样这个题就答完整了。
