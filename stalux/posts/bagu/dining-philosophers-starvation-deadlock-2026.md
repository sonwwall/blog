# 第十八节：哲学家就餐问题：什么情况下会触发饥饿和死锁？

哲学家就餐问题是并发控制里最经典的一道题。

它表面上是在讨论 5 个哲学家和 5 把叉子，实际上对应的是这样一类系统：

- 有多个执行流同时竞争有限资源
- 每个执行流要想继续工作，必须一次拿到多份资源
- 拿资源本身也需要时间和协调成本

如果把“拿叉子”换成“拿磁盘、拿连接、拿锁、拿文件句柄”，这个问题马上就和真实系统连起来了。

这一节主要围绕 6 个问题展开：

1. 哲学家就餐问题到底在抽象什么
2. 为什么“拿叉子”这一步才是整个问题的核心
3. 什么情况下会触发死锁
4. 什么情况下会触发饥饿
5. 活锁和死锁、饥饿分别是什么关系
6. 在 Go 里通常用什么思路避免这些问题

## 1. 先把模型说清楚

这个模型通常设定为：

- 一张圆桌，5 个哲学家
- 相邻两个哲学家之间放 1 把叉子，一共 5 把
- 每个哲学家只有在同时拿到左右两把叉子时才能吃面
- 不吃面的时候就思考

所以每个哲学家都会在三种状态之间切换：

- `Thinking`
- `Hungry`
- `Eating`

用 Go 表达可以写成：

```go
type State int

const (
	Thinking State = iota
	Hungry
	Eating
)
```

这三个状态已经足够表达绝大多数分析。

## 2. 为什么问题难点不在“吃面”，而在“拿叉子”

很多人第一次看这个题，会把注意力放在“谁在吃”上。

但真正的难点其实在于：

- 拿叉子不是零成本动作
- 拿左叉和拿右叉通常不是同一个原子动作
- 一旦中途拿到一半资源，就会影响别人

这正是并发控制里最麻烦的地方。

现实系统里也一样：

- 线程去拿磁盘、网络连接、数据库连接池，本身就有等待成本
- 线程往往不是一次性拿全所有资源，而是先拿一个，再去等另一个
- 中间一旦发生阻塞，就可能把系统拖进更复杂的等待关系

所以哲学家就餐问题的本质不是“谁吃饭”，而是**多个线程如何安全地获取多份互斥资源**。

## 3. 先看一个最朴素、也最危险的实现

先假设每个哲学家都是一个 goroutine，每把叉子都是一把锁。

我们先定义数据结构：

```go
type Fork struct {
	mu sync.Mutex
}

type Philosopher struct {
	id    int
	left  *Fork
	right *Fork
	state State
}
```

再写一个最朴素的流程：

```go
func (p *Philosopher) dine() {
	for {
		p.think()
		p.left.mu.Lock()
		p.right.mu.Lock()

		p.eat()

		p.right.mu.Unlock()
		p.left.mu.Unlock()
	}
}
```

这段代码看起来很自然：

- 先思考
- 拿左边叉子
- 再拿右边叉子
- 吃完后放回

但它恰好就是最容易触发死锁的写法。

## 4. 什么情况下会触发死锁

最典型的死锁场景是：

1. 5 个哲学家几乎同时进入饥饿状态
2. 每个人都先成功拿到了自己左边的叉子
3. 接着每个人都去等自己右边的叉子
4. 但右边的叉子此时都已经被邻居拿走了

于是系统进入这样一种状态：

- 每个人都持有一部分资源
- 每个人都在等待别人释放资源
- 没有人能够完成下一步

这就是**死锁**。

可以看到，死锁不是“线程都停住了”这么简单，它更准确的定义是：

**线程之间互相等待资源，但没有任何一个线程能够主动打破这个等待环。**

## 5. 死锁为什么会发生：4 个必要条件

教材里通常把死锁概括成 4 个基本条件：

1. 互斥
2. 持有并等待
3. 不可抢占
4. 循环等待

放到哲学家就餐问题里分别就是：

### 5.1 互斥

一把叉子同一时间只能给一个哲学家使用。

### 5.2 持有并等待

哲学家已经拿到左叉，但还在等右叉。

### 5.3 不可抢占

已经拿到手的叉子，别人不能强行抢走。

### 5.4 循环等待

0 等 1 的叉子，1 等 2 的叉子，2 等 3 的叉子，3 等 4 的叉子，4 又等 0 的叉子。

一旦形成这个环，系统就卡死了。

所以面试里如果被问“为什么 5 个哲学家都同时去拿叉子会死锁”，答案不是一句“因为大家都拿不到”，而是：

**因为在非抢占的互斥资源系统里，如果每个线程都先拿到部分资源，再去等待下一份资源，就可能形成循环等待。**

## 6. 饥饿是什么，它和死锁不一样

饥饿指的是：

**线程一直拿不到自己需要的资源，因此长期无法向前推进。**

它和死锁的区别在于：

- 死锁是大家都走不动
- 饥饿是系统整体还在运行，但某个线程总是轮不到

比如下面几种情况都可能导致饥饿：

- 某个哲学家优先级太低，总是被邻居抢先
- 调度器一直偏向一侧，让某几个哲学家反复先拿到资源
- 资源释放后总是被同一批线程快速再次占有

所以饥饿更像一种**局部不公平**：

- 系统没有完全停掉
- 但总有人一直吃不上饭

## 7. 活锁为什么也常被放在这个题里一起讲

活锁经常被看成饥饿的一种特殊形式。

它的特点是：

- 所有线程都在“积极行动”
- 但这些行动无法让系统真正推进

比如每个哲学家都很礼貌：

- 发现邻居也想要叉子，就把自己手里的叉子让出去
- 让完之后又重新尝试获取
- 所有人都一直重复“拿起、放下、再尝试”

这样做不会像死锁那样彻底卡住，因为线程都在运行。

但结果还是没人真正稳定吃到面，这就叫**活锁**。

所以三者的关系可以记成：

- **死锁**：大家都卡住
- **饥饿**：有人长期推进不了
- **活锁**：大家都在动，但还是推进不了，通常也会表现为饥饿

## 8. 一个更接近现实系统的理解

哲学家就餐问题之所以经典，是因为它特别像 I/O 处理场景。

线程真正消耗大量时间的部分，往往不是“拿资源”本身，而是：

- 拿到资源之后进行计算
- 拿到资源之后发起 I/O
- 拿到资源之后处理业务逻辑

但系统复杂度恰恰又集中在“拿资源”这一步。

因为：

- 资源获取顺序不一致会出问题
- 一次拿一半资源会出问题
- 获取失败后的重试策略也会出问题

所以这个题的关键不在于“面怎么吃”，而在于**资源申请阶段如何设计并发协议**。

## 9. Go 里最常见的几种规避思路

### 9.1 规定统一的加锁顺序

最常见的方法是给所有资源编号，然后规定：

- 永远先拿编号小的
- 再拿编号大的

这样就消除了循环等待。

例如：

```go
func lockTwo(a, b *Fork, aID, bID int) func() {
	if aID < bID {
		a.mu.Lock()
		b.mu.Lock()
		return func() {
			b.mu.Unlock()
			a.mu.Unlock()
		}
	}

	b.mu.Lock()
	a.mu.Lock()
	return func() {
		a.mu.Unlock()
		b.mu.Unlock()
	}
}
```

只要所有 goroutine 都遵守同一个资源顺序，死锁环就很难形成。

### 9.2 一次性判断两把叉子是否都可用

另一种思路是：

- 不先拿一把再等另一把
- 而是进入临界区后一次判断两把是否都空闲
- 两把都可用才同时占有，否则直接退出重试

这相当于把“拿两把叉子”做成一个更接近原子的动作。

可以用一个总锁保护叉子状态：

```go
type Table struct {
	mu    sync.Mutex
	forks [5]int // -1 表示空闲，否则记录持有者 id
}

func (t *Table) tryTakeBoth(id int, left int, right int) bool {
	t.mu.Lock()
	defer t.mu.Unlock()

	if t.forks[left] != -1 || t.forks[right] != -1 {
		return false
	}

	t.forks[left] = id
	t.forks[right] = id
	return true
}

func (t *Table) putBoth(id int, left int, right int) {
	t.mu.Lock()
	defer t.mu.Unlock()

	if t.forks[left] == id {
		t.forks[left] = -1
	}
	if t.forks[right] == id {
		t.forks[right] = -1
	}
}
```

这种方式牺牲了一部分并行度，但逻辑更清晰，也更容易避免死锁。

### 9.3 使用带超时的获取策略

如果拿不到资源，就主动放弃，过一会儿再试，也能降低一直卡住的概率。

Go 的 `sync.Mutex` 没有内置 `TryLock` 的常规通用组合式接口来优雅处理多资源超时获取，所以工程里更常见的做法是：

- 用 `channel` 表达资源令牌
- 配合 `select + time.After`
- 拿不到就回退

例如把叉子抽象成容量为 1 的 channel：

```go
func takeWithTimeout(fork chan struct{}, timeout time.Duration) bool {
	select {
	case <-fork:
		return true
	case <-time.After(timeout):
		return false
	}
}
```

这种方式不是为了让代码更“花哨”，而是为了显式表达：

- 拿资源可能失败
- 失败后要及时回退
- 不要无限等待

### 9.4 让一个协调者统一发放资源

再进一步，可以干脆引入一个调度者：

- 哲学家不直接抢叉子
- 而是先向调度者申请
- 调度者确认左右叉子都空闲后再授权

这本质上是把“分布式抢资源”变成“中心化调度资源”。

实现上可以用：

- 一个管理 goroutine
- 若干申请 channel
- 若干释放 channel

这样写的好处是正确性更容易证明，坏处是中心协调者可能成为瓶颈。

## 10. 为什么“给整个过程加一把大锁”虽然能解决，但通常不是最优

还有一种最简单的办法：

- 所有哲学家在吃面全过程外面套一把总锁

这样当然不会死锁，因为同一时间只允许一个哲学家拿叉子、吃面、放叉子。

但问题也很明显：

- 并发度几乎没了
- 本来可以并行吃面的相邻外哲学家也被串行化了

所以它只是一个“绝对安全但性能保守”的方案。

这类解法在工程里当然也会用，但通常只适合：

- 资源冲突很频繁
- 正确性远比吞吐量更重要
- 临界区本身很短

## 11. 如果允许抢占，为什么又可能从死锁走向活锁

有人会想，既然死锁来自“拿了不放”，那就让线程在拿不到第二把叉子时把第一把也放回去。

这确实打破了“持有并等待”，但新的问题是：

- 大家都拿一下
- 发现冲突
- 又都放下
- 然后再同时重试

如果重试节奏过于一致，就可能反复互相谦让，谁也吃不上。

这就是为什么：

- **死锁后的粗暴回退策略**
- **过于一致的重试策略**

都有概率把系统带进活锁。

工程上常见的缓解办法是：

- 加随机退避
- 加超时
- 加优先级
- 加统一调度

核心目标就是避免所有线程以完全相同的节奏反复碰撞。

## 12. 所以到底什么情况下会触发饥饿和死锁

可以把这道题最后收束成两句话。

### 12.1 什么情况下会触发死锁

当系统满足下面这些条件时，就容易触发死锁：

- 资源互斥
- 线程先持有部分资源，再等待其他资源
- 已持有资源不能被强行抢占
- 等待关系形成环

在哲学家就餐问题里，最经典的触发方式就是：

- 大家都先拿左叉
- 再去等右叉

### 12.2 什么情况下会触发饥饿

当某个线程长期拿不到所需资源时，就会触发饥饿。

常见诱因包括：

- 调度不公平
- 优先级长期偏低
- 重试策略让同一个线程总是慢一步
- 活锁导致系统一直在动，但某个线程始终无法完成资源获取

所以从更大的概念上说：

- **死锁和活锁都可能表现为饥饿**
- **但不是所有饥饿都是死锁**

## 13. 这一节怎么记最稳

如果只记一句话，我建议记这个：

**哲学家就餐问题的核心，不是吃面，而是多个线程如何以正确顺序、正确协议去获取多份互斥资源。**

继续展开，就是下面这几条：

- 一次拿一半资源，最容易引出死锁
- 调度长期不公平，最容易引出饥饿
- 为了避免死锁而频繁回退，如果回退策略设计不好，又可能引出活锁
- 真正有效的解法，本质上都是在设计更好的资源分配协议

如果再把它和系统设计连起来，可以继续问自己一个很实用的问题：

**资源获取的代价到底大不大？**

如果拿资源非常快，而主要开销集中在计算本身，那么调度目标会更偏向 CPU 利用率。

如果拿资源本身就很慢，而且经常伴随 I/O 阻塞，那么资源分配协议的设计就会直接决定系统是否稳定。
