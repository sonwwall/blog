# 第二十二节：TLB和大页分页：为什么MMU查页表还需要缓存？

这一节主要围绕 8 个问题展开：

1. `MMU` 在地址转换里负责什么
2. 为什么只靠页表会有性能问题
3. `TLB` 是什么，以及它缓存了什么
4. `TLB` 命中、软失效、硬失效分别是什么意思
5. `TLB` 的缓存条目有哪些映射方式
6. 多级页表和 `TLB` 是怎么配合的
7. 大页分页为什么能减少 `TLB` 压力
8. `Go` 程序默认需不需要开启大内存分页

## 1. 先回顾：虚拟地址如何变成物理地址

现代操作系统通常给每个进程提供独立的虚拟地址空间。  
程序看到的是虚拟地址，但真正访问内存时，硬件最终需要拿到物理地址。

分页系统里，一个虚拟地址一般可以拆成两部分：

- 页号，也就是 `Page Number`
- 页内偏移，也就是 `Offset`

页号用来查页表，页内偏移不需要转换。

如果页表里记录：

- 虚拟页 `Page Number = 100`
- 对应物理页框 `Frame Number = 20`

那么地址转换时，只需要把：

- `Page Number` 替换成 `Frame Number`
- `Offset` 保持不变

最后得到的就是物理地址。

所以可以把地址转换先记成一句话：

- **虚拟地址 = 页号 + 偏移量**
- **物理地址 = 页框号 + 偏移量**

## 2. `MMU` 在这里负责什么

`MMU` 是 `Memory Management Unit`，也就是内存管理单元。

它可以理解成：

- CPU 和内存之间的地址翻译硬件

CPU 执行程序时发出的通常是虚拟地址。  
`MMU` 收到虚拟地址后，会根据页表把它翻译成物理地址，再让 CPU 访问真正的内存。

大致流程是：

1. CPU 发出虚拟地址
2. `MMU` 拆出页号和偏移量
3. `MMU` 根据页号查页表
4. 找到对应的页框号
5. 页框号和偏移量拼成物理地址
6. 访问真实内存

所以 `MMU` 的本质职责是：

- **把进程看到的虚拟地址，转换成机器真正使用的物理地址**

## 3. 为什么只靠页表会有性能问题

指令执行速度非常快，而内存访问相对慢很多。

如果 CPU 每次访问内存都要先做一次页表查询，就会出现一个尴尬问题：

- 本来访问一次内存就已经有成本
- 现在为了访问这次内存，还要先额外访问内存中的页表

也就是说，原本一次内存访问可能变成：

1. 先访问页表
2. 再访问真正的数据

如果是多级页表，情况还会更明显。

比如四级页表下，一次地址翻译可能要连续查多层页表，最后才访问真正数据。  
这样每条指令、每次读写都走完整页表链路，性能会很差。

所以问题变成：

- **页表能完成地址转换，但页表查询不能每次都完整走一遍**

这就是 `TLB` 出现的原因。

## 4. `TLB` 是什么

`TLB` 是 `Translation Lookaside Buffer`，通常翻译成：

- 转译后备缓冲区
- 转址旁路缓存
- 页表缓存

从用途上看，最容易理解成：

- **放在 `MMU` 附近的一个小型高速缓存**

它缓存的不是普通数据，而是地址翻译结果：

- `Page Number -> Frame Number`

也就是：

- 虚拟页号到物理页框号的映射关系

一个 `TLB` 条目通常可以理解成：

- 虚拟页号
- 物理页框号
- 权限位
- 有效位
- 其他和地址翻译相关的状态位

这样下次再访问同一个虚拟页时，`MMU` 就不需要先去内存里查页表了，而是先查 `TLB`。

## 5. 有了 `TLB` 后，地址转换流程变成什么

有 `TLB` 以后，地址转换可以理解成：

1. CPU 发出虚拟地址
2. `MMU` 拆出 `Page Number` 和 `Offset`
3. 先用 `Page Number` 查 `TLB`
4. 如果 `TLB` 命中，直接得到 `Frame Number`
5. 如果 `TLB` 未命中，再去查页表
6. 最后用 `Frame Number + Offset` 得到物理地址

所以 `TLB` 的作用就是：

- **根据输入的 `Page Number`，尽快找到对应的 `Frame Number`**

这和 CPU 缓存的思想非常像：

- CPU 缓存解决的是“内存数据访问太慢”
- `TLB` 解决的是“页表查询太慢”

因此，`TLB` 本质上是地址翻译路径上的缓存。

## 6. `TLB` 为什么通常用硬件实现

地址翻译发生得太频繁了。

程序执行过程中，取指令、读数据、写数据都可能涉及地址转换。  
如果 `TLB` 查询还要靠软件慢慢处理，那么性能收益就被抵消了。

所以 `TLB` 通常由硬件实现，并且会放在 CPU 核心附近。  
多核 CPU 中，常见做法是：

- 每个核心都有自己独立的 `TLB`
- `TLB` 也可能像 CPU 缓存一样做分级
- 有的架构会区分指令 `TLB` 和数据 `TLB`

这背后的原因和 `L1 Cache` 类似：

- 离 CPU 越近越快
- 容量越小越容易做快
- 高频路径必须尽量硬件化

## 7. `TLB` 命中和失效

### 7.1 `TLB` 命中

如果要访问的 `Page Number` 已经在 `TLB` 中，并且权限检查也通过，就叫：

- `TLB Hit`

这时 `MMU` 可以直接拿到 `Frame Number`，不需要完整查页表。

### 7.2 `TLB` 软失效

如果 `TLB` 中没有这个映射，但页表里有，并且对应的物理页框还在内存中，就可以理解成：

- 软失效

它的特点是：

- 数据还在内存里
- 只是 `TLB` 缓存里没有
- 需要查页表，把映射重新放进 `TLB`

这里通常只涉及页表查询和 `TLB` 填充，不需要从磁盘加载数据。

### 7.3 `TLB` 硬失效

如果页表中发现目标页不在物理内存中，需要从磁盘或交换区加载，就可以理解成：

- 硬失效

这通常会触发缺页异常，由操作系统介入处理。

它的成本远高于软失效，因为可能涉及：

- 线程阻塞
- 磁盘 I/O
- 页面换入
- 页表更新
- `TLB` 更新
- 调度器重新安排执行

需要注意的是：

- 线程不可能从休眠态“不排队”就直接进入执行态
- 硬失效相对耗时，因为它可能需要等待 I/O 和调度

所以可以记成：

- **软失效：页还在内存，只是 `TLB` 没缓存**
- **硬失效：页不在内存，需要从磁盘加载**

## 8. `TLB` 条目的缓存置换

`TLB` 容量有限，不可能保存所有虚拟页到物理页框的映射。

当新的映射要放进 `TLB`，但 `TLB` 已经满了，就必须选择一个旧条目覆盖掉。  
这个过程可以叫：

- 缓存置换

常见思路包括：

- `LRU`，优先淘汰最久未使用的条目
- 近似 `LRU`，用更低成本模拟最近使用情况
- 随机置换
- 按硬件实现定制的策略

真正的 `TLB` 置换通常由硬件和操作系统协同完成，不一定会严格使用软件意义上的完整 `LRU`。

## 9. `TLB` 有哪些映射方案

从缓存结构角度看，`TLB` 条目可以类比 CPU 缓存条目。  
常见映射思路有 3 类：

- 全相联映射
- 直接映射
- `n` 路组相联映射

### 9.1 全相联映射

全相联映射的意思是：

- 一个 `Page Number` 可以放到任何一个 `TLB` 条目中

它的优点是灵活，冲突少。  
但问题是查找时需要在多个条目中比较标签。

在硬件里可以做并行比较，但并行比较越多，硬件复杂度和功耗越高。  
所以全相联更适合容量比较小、对速度要求极高的缓存。

可以记成：

- **灵活性强**
- **命中率相对好**
- **硬件成本更高**

### 9.2 直接映射

直接映射的意思是：

- 一个 `Page Number` 只能放到固定的某一个条目中

它通常可以写成类似哈希函数的形式：

```text
TLB 条目号 = Page Number % 条目数量
```

比如 `TLB` 有 `64` 个条目，要查找 `Page Number = 100`：

```text
100 % 64 = 36
```

那么它只能去第 `36` 个条目里找。

直接映射的优点是：

- 实现简单
- 查找快
- 成本低

缺点是：

- 冲突更容易发生

比如很多热点页刚好都映射到同一个条目，那么它们会不断互相覆盖，导致命中率下降。  
这种情况下，即使程序访问的数据总量不大，也可能因为映射冲突导致 `TLB` 频繁失效。

### 9.3 `n` 路组相联映射

`n` 路组相联映射介于全相联和直接映射之间。

它的意思是：

- 一个 `Page Number` 不是只能放一个位置
- 也不是能放任意位置
- 而是只能放到固定的一组候选位置中

比如某个设计里，一个页号可以映射到连续的 `n` 个位置。  
如果 `TLB` 有 `64` 个条目，要查找 `Page Number = 100`，基础位置是：

```text
100 % 64 = 36
```

那么：

- 如果是 `4` 路组相联，可以只看 `36, 37, 38, 39`
- 如果是 `8` 路组相联，可以只看 `36 ~ 43`

它的好处是：

- 比直接映射冲突少
- 比全相联硬件成本低
- 是工程上很常见的折中方案

所以三者可以这样对比：

| 映射方式 | 一个页号能放哪里 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 全相联映射 | 任意条目 | 冲突少，命中率好 | 硬件成本高 |
| 直接映射 | 唯一固定条目 | 简单、快 | 冲突多 |
| `n` 路组相联 | 固定一组候选条目 | 折中方案 | 仍可能冲突 |

## 10. 多级页表和 `TLB` 是什么关系

多级页表解决的是：

- 页表本身太大的问题

它把一张大页表拆成多层结构，按需分配真正使用到的页表页。

但多级页表也带来一个问题：

- 查页表的链路变长了

比如一级页表可能只查一次表。  
多级页表可能要先查一级页表，再查二级页表，甚至继续查三级、四级页表。

所以多级页表和 `TLB` 的关系可以这样理解：

- 多级页表节省页表空间
- `TLB` 加速页表查询

如果没有 `TLB`，多级页表的查询成本会非常明显。  
如果 `TLB` 命中率高，大多数访问就不用真的走完整多级页表。

这也是为什么 `TLB` 对现代虚拟内存系统非常重要。

## 11. 大页分页解决什么问题

常见页大小是 `4KB`。  
如果一个进程需要大量内存，比如 `1GB`，那么页数大约是：

```text
1GB / 4KB = 262144 页
```

如果 `TLB` 只有 `1024` 个条目，那么平均看，一个 `TLB` 条目背后要覆盖很多虚拟页。  
当程序访问范围很大时，就容易出现 `TLB` 冲突和失效。

大页分页的思路是：

- 把页从 `4KB` 变成更大的单位

比如使用 `2MB` 或 `4MB` 的大页。  
如果页大小从 `4KB` 变成 `4MB`，同样大小的内存区域需要的页数就会减少 `1024` 倍。

页数减少以后，会带来几个好处：

- 页表项数量减少
- 页表占用内存减少
- 同一个 `TLB` 条目能覆盖更大的内存范围
- `TLB` miss 的概率可能下降
- 地址翻译成本可能降低

这就是大页分页的核心收益：

- **用更大的页，减少页表和 `TLB` 压力**

## 12. 大页分页不是越大越好

大页也有代价。

页越大，内存管理的粒度越粗。  
如果程序只用了大页里的一小部分，剩下的空间也可能被占住，造成浪费。

常见代价包括：

- 内部碎片可能增加
- 小堆、小对象场景可能浪费内存
- 内存回收和压缩更复杂
- 需要连续物理内存时，分配难度更高
- 某些负载下延迟可能变差

所以大页分页适合的不是“所有程序”，而是：

- 内存需求大
- 访问比较密集
- 热点范围大
- `TLB` miss 成本明显
- 能接受一定额外内存开销

比如：

- 搜索引擎
- 数据库
- 大型缓存系统
- 大内存分析任务
- 高并发下的大堆服务

如果程序内存很小，或者访问很稀疏，大页可能收益不明显，甚至会浪费更多内存。

## 13. Linux 里大页分页有两类常见方式

Linux 里经常会看到两类概念：

- 显式大页，也就是 `HugeTLB Pages`
- 透明大页，也就是 `Transparent Huge Pages, THP`

### 13.1 显式大页

显式大页需要提前保留一定数量的大页。

例如：

```bash
sudo sysctl -w vm.nr_hugepages=2048
```

这表示向系统申请保留一定数量的 HugeTLB 大页。

它的特点是：

- 更可控
- 常用于数据库、虚拟机、专门优化过的服务
- 需要应用或运行环境明确使用
- 配置不当会导致内存被预留但没有被有效使用

查看大页状态时，可以用：

```bash
grep Huge /proc/meminfo
```

常见字段包括：

- `HugePages_Total`：系统预留的大页总数
- `HugePages_Free`：当前空闲的大页数量
- `HugePages_Rsvd`：已被预留但尚未真正分配的大页
- `Hugepagesize`：每个大页的大小
- `Hugetlb`：HugeTLB 占用的总量
- `AnonHugePages`：匿名内存使用透明大页的量

如果 `Hugepagesize = 2048 kB`，`HugePages_Total = 2048`，那么预留的大页总容量大约是：

```text
2048 * 2048KB = 4GB
```

### 13.2 透明大页

透明大页 `THP` 是 Linux 自动尝试把普通页合并成大页的机制。

它的特点是：

- 应用通常不需要显式调用 HugeTLB 接口
- 系统会根据策略自动尝试使用大页
- 使用门槛低
- 但可能带来额外内存占用或延迟抖动

可以通过类似文件查看或配置：

```bash
cat /sys/kernel/mm/transparent_hugepage/enabled
cat /sys/kernel/mm/transparent_hugepage/defrag
```

常见策略包括：

- `always`：尽量总是使用透明大页
- `madvise`：只有应用明确建议时才使用
- `never`：不主动使用透明大页

生产环境里更常见的思路不是盲目 `always`，而是根据应用负载和压测结果决定。

## 14. 面试里怎么回答“大页什么时候用”

可以这样回答：

> 大页分页主要解决页表过大和 `TLB` 命中率不足的问题。普通 `4KB` 页在大内存程序里会产生非常多页表项，同一个 `TLB` 能覆盖的内存范围有限，容易增加地址翻译成本。大页把页变成 `2MB`、`4MB` 甚至更大后，可以减少页表项数量，让一个 `TLB` 条目覆盖更大内存范围，从而提升大内存密集访问程序的性能。

然后补充权衡：

> 但大页不是越多越好。页变大后，内存分配粒度也变粗，可能造成内部碎片和额外内存占用。它更适合数据库、搜索引擎、大缓存、大堆服务这类内存需求大、访问比较密集的场景。普通小服务默认不一定需要开启，最好结合压测、`TLB miss`、内存占用和延迟指标判断。

如果再追问 Linux 怎么开，可以继续说：

> Linux 里要区分显式 HugeTLB 和透明大页 THP。`vm.nr_hugepages` 是预留显式大页，适合明确知道应用会使用大页的场景；THP 则是内核自动尝试使用大页，配置更方便，但要注意内存开销和延迟抖动。

## 15. 最后回答：`Go` 默认需不需要开启大内存分页

简短回答：

- **Go 程序默认不需要手动开启显式大页分页**
- **不要一上来就配置 `vm.nr_hugepages` 给普通 Go 服务用**
- **大堆、内存密集型 Go 服务可以考虑透明大页 `THP`，但要压测验证**

更准确地说：

### 15.1 普通 Go 服务

普通 Go Web 服务、后台服务、命令行程序，默认不需要专门开启大页。

原因是：

- Go runtime 自己管理堆、栈和 GC
- 普通服务的堆不一定大到明显受 `TLB` 限制
- 显式预留 HugeTLB 大页可能造成内存浪费
- 配置不当还可能影响同机器上的其他进程

所以默认建议是：

- **先按系统默认运行**
- **观察内存、延迟、吞吐、GC 指标**
- **有明确瓶颈再考虑大页**

### 15.2 大内存 Go 服务

如果 Go 程序堆很大，比如长期使用 `1GB` 以上内存，并且访问比较密集，那么大页可能有收益。

典型场景包括：

- 大缓存服务
- 搜索索引
- 内存数据库组件
- 大规模数据处理
- 高 QPS 且堆很大的服务

这种情况下可以考虑：

- 让 Linux 使用合适的 `THP` 策略
- 调整 `/sys/kernel/mm/transparent_hugepage/defrag`
- 观察 `AnonHugePages`
- 结合 `perf` 观察 `dTLB-load-misses` 等指标
- 对比开启前后的吞吐、P99 延迟和内存占用

### 15.3 Go 1.21 之后要特别注意

Go 官方文档提到，Go 1.21 之后 runtime 对 Linux 透明大页的处理更明确。  
大堆程序可能因为更好的大页利用而获得吞吐或延迟收益，但某些 Linux 默认配置也可能带来额外内存占用。

如果升级 Go 后发现内存占用变高，可以考虑：

- 调整 Linux 的透明大页配置
- 调整 `khugepaged/max_ptes_none`
- 必要时用 `GODEBUG=disablethp=1` 禁用 Go 堆的透明大页

但 `GODEBUG=disablethp=1` 更像兼容性或临时规避手段，不应该作为长期默认调优方案。

所以最终结论可以这样记：

> `Go` 默认不需要手动开启大内存分页。普通 Go 服务按系统默认运行即可；只有当 Go 程序是大堆、内存密集型，并且压测证明 `TLB miss` 或地址翻译成本明显时，才考虑调整透明大页。显式 HugeTLB 大页更不应该随便开，因为它需要预留内存，适合有明确收益和明确配置能力的场景。

## 16. 这一节先记住的点

- `MMU` 负责把虚拟地址翻译成物理地址
- 虚拟地址可以拆成 `Page Number + Offset`
- 物理地址可以拆成 `Frame Number + Offset`
- 页表记录 `Page Number -> Frame Number`
- `TLB` 缓存页表查询结果，加速地址翻译
- `TLB` 命中时，不需要完整查页表
- 软失效表示页还在内存，只是 `TLB` 没有缓存
- 硬失效表示页不在内存，可能需要磁盘 I/O 和调度
- `TLB` 映射方案包括全相联、直接映射和 `n` 路组相联
- 多级页表节省空间，但查询路径更长，所以更依赖 `TLB`
- 大页分页可以减少页表项和 `TLB` 压力
- 大页适合大内存、密集访问程序，不适合所有程序默认开启
- `Go` 普通服务默认不需要手动开启大页，大堆服务要结合压测决定
