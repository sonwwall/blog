# 第八节：软件的安装：编译安装和包管理器安装有什么优势和劣势？

Linux 中安装软件，常见有两种思路：

- 使用包管理器安装
- 下载源码后自己编译安装

这一节主要围绕 4 个点展开：

1. Linux 下常见的软件包和包管理器是什么
2. 包管理器安装通常能解决什么问题
3. 编译安装的基本流程是什么
4. 编译安装和包管理器安装各自有什么优势和劣势

## 1. Linux 下常见的软件安装方式

先记一个整体结论：

**Linux 中安装软件，一般不是双击安装包，而是通过“包管理器”或者“源码编译”来完成。**

### 1.1 什么是软件包

可以把软件包理解成：

- 已经整理好的程序文件
- 配套的配置、脚本、说明信息
- 以及安装、卸载所需的元数据

Linux 下常见的两类基础包格式是：

- `rpm`
- `dpkg`

更准确地说：

- `rpm` 对应的是 RPM 系的软件生态，常见于 `CentOS`、`Red Hat`、`Fedora`
- `dpkg` 对应的是 Debian 系的软件生态，常见于 `Debian`、`Ubuntu`

### 1.2 `dpkg` 和 `rpm` 提供什么能力

`dpkg` 和 `rpm` 都提供类似的基础能力：

- 查询某个软件包是否已经安装
- 查看当前安装了哪些软件包
- 给定一个软件包文件，执行安装
- 删除一个已经安装好的软件包

例如在 Debian/Ubuntu 体系里，`dpkg` 常用于本地包管理底层操作。  
在 RPM 体系里，`rpm` 扮演的是类似角色。

但它们有一个共同问题：

**它们更偏底层，能管理包本身，但不擅长自动解决复杂依赖。**

## 2. 为什么后来更多人使用 `apt` 和 `yum`

实际工作里，很多软件并不是单独存在的。  
一个包往往会依赖很多其他包。

例如：

- A 软件依赖 B 库
- B 库又依赖 C 和 D
- 如果手工逐个安装，过程会很繁琐

所以后来更常用的是：

- Debian/Ubuntu 体系中的 `apt`
- Red Hat/CentOS 体系中的 `yum`

它们本质上是更高层的包管理工具。

### 2.1 `apt` 和 `yum` 的核心价值

这类高级包管理器主要帮你解决两个问题：

- 下载
- 依赖

也就是说，用户只需要说“我要安装这个软件”，包管理器会去：

- 查询软件仓库
- 下载对应版本的软件包
- 自动拉取依赖
- 按正确顺序安装

这就是为什么在大多数场景里，包管理器安装比手工装包省事得多。

### 2.2 `yum` 和 `apt` 分别是什么

#### `yum`

`yum` 可以理解成 RPM 体系下常见的高级包管理工具。

它最重要的作用是：

- 从仓库下载软件
- 自动处理依赖关系

#### `apt`

`apt` 是 Debian 及其衍生 Linux 发行版下常见的高级包管理工具。

它的英文全称通常写作：

```text
Advanced Packaging Tools
```

同样，它的核心价值也是：

- 从软件源获取软件
- 自动解决依赖
- 统一管理安装、删除、查询、升级

## 3. `apt` 的常见操作

这一节素材里主要展示的是 `apt`，所以这里重点整理 `apt` 的常见命令。

### 3.1 安装软件

例如安装 `vim`：

```bash
sudo apt install vim
```

这个命令会：

- 检查软件源中是否存在 `vim`
- 检查本机是否已安装
- 自动分析依赖关系
- 如有需要自动下载安装依赖包

### 3.2 删除软件

如果只是普通删除，可以使用：

```bash
sudo apt remove vim
```

它的特点是：

- 删除程序本身
- 某些配置文件可能还会保留

如果希望连配置也一起清掉，可以使用：

```bash
sudo apt purge vim
```

所以二者区别可以简单记成：

- `remove`：偏向卸载程序
- `purge`：偏向更彻底地删除，包括配置

### 3.3 查看某个包是否安装

在 Ubuntu 体系中，底层可以用 `dpkg` 查询。

例如：

```bash
dpkg -l vim
```

这个命令可以查看：

- 当前系统中是否存在该包
- 包的状态
- 版本
- 架构

### 3.4 查询有哪些可安装的软件包

例如：

```bash
apt search mysql
```

或者直接查某个具体包：

```bash
apt list mysql-server
```

这些命令常用来：

- 搜索仓库里有哪些候选软件
- 查看某个包是否存在
- 查看包来自哪个发行版仓库

### 3.5 先确认系统版本再装包

包管理器安装和系统发行版、版本强相关，所以有时需要先看当前系统版本。

例如：

```bash
lsb_release -a
```

这样可以看到：

- 发行版名称
- 版本号
- 代号

比如 Ubuntu `20.04` 的代号是 `focal`。  
很多包仓库就是按这个代号区分版本的。

## 4. 编译安装是什么

包管理器安装的前提是：

- 别人已经提前把软件编译好
- 并打成适合你系统的安装包

那为什么还会有编译安装？

### 4.1 为什么需要编译安装

因为一个程序要运行在很多平台上，而不同平台之间存在很多差异：

- CPU 指令集不同
- 操作系统不同
- 可执行文件格式不同
- 系统库版本不同

所以软件发布方、发行版维护者通常需要提前做大量适配工作，把源码编译成适合某个平台的二进制包。

但现实里仍然会有两类情况让我们必须或倾向于编译安装：

- 某个版本没有现成的软件包
- 需要很强的定制化能力

这就是编译安装存在的原因。

## 5. 编译安装 `nginx` 的典型流程

这一节的素材用 `nginx` 举例，很适合说明编译安装的过程。

### 5.1 第一步：下载源码

编译安装一般先从官网拿源码压缩包。

例如：

```bash
wget http://nginx.org/download/nginx-1.19.2.tar.gz
```

这一步做的事就是：

- 获取源码压缩包
- 保存到当前目录

### 5.2 第二步：解压源码

源码下载下来后，需要先解压：

```bash
tar -xzvf nginx-1.19.2.tar.gz
```

解压后通常会得到一个源码目录，例如：

```text
nginx-1.19.2/
```

然后进入该目录：

```bash
cd nginx-1.19.2
```

### 5.3 第三步：配置编译参数并检查依赖

源码目录里通常会有 `configure` 脚本。

先看看它支持哪些参数：

```bash
./configure --help | head -n 10
```

这里常见的参数包括：

- `--prefix`
- `--conf-path`
- `--error-log-path`
- `--pid-path`

它们的意义是：

- 指定安装目录
- 指定配置文件位置
- 指定日志位置
- 指定运行时文件位置

如果直接执行：

```bash
./configure
```

这个过程本质上是在做两件事：

- 检查当前系统环境
- 检查编译依赖是否满足

例如有时会直接报错：

```text
C compiler cc is not found
```

这说明当前机器缺少 C 编译器。

在 Ubuntu 上常见的解决办法是安装：

```bash
sudo apt install build-essential
```

`build-essential` 可以理解成一组基础编译工具集合，里面通常包括：

- `gcc`
- `g++`
- `make`
- 以及一些编译常用组件

### 5.4 缺什么依赖，就补什么依赖

编译安装最常见的问题就是依赖没装齐。

例如 `nginx` 在配置过程中，可能会报类似错误：

```text
the HTTP rewrite module requires the PCRE library
```

这说明当前系统缺少 `PCRE` 相关库。

这时可以先搜索相关包：

```bash
apt search pcre
```

然后安装开发包，例如：

```bash
sudo apt install libpcre3 libpcre3-dev
```

这个过程很典型，也很能说明编译安装的特点：

- 报错往往不是“软件本身错了”
- 而是环境里缺少编译所需依赖
- 需要你自己判断并补齐

### 5.5 第四步：编译和安装

当 `./configure` 通过后，后面通常就进入编译和安装阶段。

常见流程是：

```bash
make
sudo make install
```

可以简单理解成：

- `make`：真正编译源码
- `make install`：把编译后的程序复制到目标目录

### 5.6 安装完成后的一个常见处理

如果最终可执行文件在：

```text
/usr/local/nginx/sbin/nginx
```

而你希望直接在终端输入 `nginx` 就能运行，可以建立软链接：

```bash
ln -sf /usr/local/nginx/sbin/nginx /usr/local/sbin/nginx
```

这样系统在常见路径里就能找到这个命令。

## 6. 包管理器安装和编译安装各自的优势与劣势

这是本节最核心的问题。

### 6.1 包管理器安装的优势

包管理器安装最大的优点是方便。

主要体现在：

- 安装简单，命令短
- 能自动下载软件
- 能自动处理依赖
- 卸载、升级、查询都比较统一
- 更适合大多数日常场景

所以在生产环境中，**如果仓库里有合适的软件包，通常优先考虑包管理器安装。**

### 6.2 包管理器安装的劣势

包管理器安装虽然方便，但也有两个明显劣势。

#### 第一，版本受仓库发布节奏限制

软件要先进仓库，一般得先被发行版维护者编译、打包、发布。

这意味着：

- 某些新版本不一定马上能装到
- 某些冷门软件可能根本没有对应包
- 某个平台上可能找不到你想要的那个版本

如果仓库里没有合适版本，就只能自己编译。

#### 第二，定制能力有限

包管理器安装的包，通常是别人已经按通用场景编译好的。

但有些软件定制程度很高，比如：

- 需要打开某个模块
- 需要关闭某个模块
- 需要指定安装路径
- 需要特定编译参数

这时别人打好的通用包可能不满足需求，就更适合编译安装。

### 6.3 编译安装的优势

编译安装的优点主要是灵活。

它的价值在于：

- 可以安装你指定的源码版本
- 可以按需启用或禁用模块
- 可以自由控制安装路径
- 可以针对业务场景做定制化编译

所以它特别适合：

- 追新版本
- 定制化部署
- 某些仓库里没有提供的场景

### 6.4 编译安装的劣势

编译安装的缺点也很明显：

- 操作步骤更多
- 要自己处理依赖
- 遇到报错需要自己排查
- 升级和卸载通常不如包管理器统一
- 可维护性和标准化通常更差

也就是说，**编译安装更灵活，但更考验环境理解和排障能力。**

## 7. 面试里怎么答

如果面试官问：**编译安装和包管理器安装有什么优势和劣势？**

可以直接答：

1. Linux 安装软件常见有两种方式，一种是包管理器安装，一种是源码编译安装
2. 包管理器安装的优点是方便，能够自动下载、自动解决依赖，安装、删除、升级都比较统一
3. 包管理器安装的缺点是受仓库版本限制，而且定制能力有限
4. 编译安装的优点是灵活，可以指定版本、指定安装路径、启用或关闭模块
5. 编译安装的缺点是步骤多，需要自己解决依赖，排错和维护成本更高

如果再展开一句，可以补充：

**通常优先用包管理器；如果仓库里没有合适版本，或者需要高度定制化，再选择编译安装。**

## 8. 一个常见排障问题

### 8.1 如果编译安装 MySQL 时发现 `libcrypt.so` 找不到，应该怎么处理

这个问题的本质通常不是 MySQL 本身有问题，而是：

- 当前系统缺少对应动态库
- 或者缺少开发包
- 或者库文件存在，但链接路径没有被正确识别

排查思路一般是：

1. 先看报错里缺的是运行库还是开发库
2. 在包管理器里搜索相关包
3. 安装对应的运行时库或开发包
4. 必要时检查库文件路径和软链接

例如在 Debian/Ubuntu 体系里，可以先搜索：

```bash
apt search libcrypt
```

如果确实缺少相关库，再安装对应软件包。

面试里如果被追问，回答重点可以放在：

- 编译安装报某个 `.so` 缺失，本质上是依赖问题
- 先搜索并安装对应库或开发包
- 如果库已经安装，还要继续检查链接路径、环境和版本兼容性
