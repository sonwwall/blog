# 第十六节：乐观锁，区块链：除了上锁还有哪些并发控制方法？

上一节我们重点讲了：

- 锁
- 信号量
- 分布式锁

这些方案的共同点是：

- 都在想办法控制多个线程或多个请求对同一份共享资源的访问顺序

但“并发控制”不一定都要靠“先锁住，别人别动”来完成。

这一节主要围绕 6 个问题展开：

1. 悲观锁和乐观锁分别在假设什么
2. 乐观锁为什么常常配合版本号使用
3. 为什么购物车、库存这类业务很适合讲乐观锁
4. 除了集中式上锁，还有没有去中心化的同步思路
5. 区块链为什么可以看成一种基于历史版本的事实链
6. 区块链解决了什么问题，又没有解决什么问题

## 1. 悲观锁和乐观锁，本质上是在做不同假设

并发控制的第一步，不是立刻选工具，而是先回答一个问题：

**你到底认为冲突是常态，还是偶发事件？**

如果你认为：

- 冲突很常见
- 别人很可能同时修改
- 一旦冲突代价很大

那你通常会更偏向**悲观锁**。

如果你认为：

- 大部分时候不会撞上冲突
- 同时修改只是少数情况
- 真冲突了再处理也来得及

那你通常会更偏向**乐观锁**。

所以这两个名字的核心，不是“心态”，而是对并发场景的不同假设。

## 2. 什么是悲观锁

悲观锁的思路可以概括成一句话：

**我先假设别人一定会和我抢，所以我先把资源锁住。**

它的核心做法是：

- 进入临界区前先加锁
- 同一时间只让一个线程或一个事务修改
- 其他人先等着

这种方式有很强的排他性。

它的优点是：

- 模型直观
- 一致性容易理解
- 修改时更保守、更稳

它的缺点是：

- 吞吐量容易下降
- 持锁时间一长，等待会越来越多
- 系统并发能力会被锁竞争限制住

所以悲观锁更像是在说：

**先同步，再修改。**

## 3. 什么是乐观锁

乐观锁的思路刚好相反：

**我先假设大部分时候不会冲突，所以先让大家改，真正提交时再检查。**

它通常不是先把资源锁住，而是：

1. 先读取当前数据
2. 在本地基于这个数据计算新结果
3. 提交时检查“我读取时的版本”是不是还有效
4. 如果版本没变，提交成功
5. 如果版本变了，说明有人抢先改过，当前提交失败，再重试或报错

所以乐观锁更像是在说：

**先修改方案，提交时校验版本。**

## 4. 为什么说乐观锁其实是在做版本控制

乐观锁最常见的实现方式，就是给数据增加一个**版本号**。

比如数据库表里除了业务字段，还会多一个字段：

```text
id | count | version
```

读取时拿到：

```text
count = 10
version = 5
```

提交更新时不是直接写：

```sql
update table set count = 9 where id = 1;
```

而是写成：

```sql
update table
set count = 9, version = 6
where id = 1 and version = 5;
```

如果更新成功，说明：

- 这条数据从你读取到提交之间，没有别人改过

如果更新影响行数是 `0`，说明：

- 版本已经不是 `5` 了
- 有人先一步提交成功
- 你的这次修改基于旧版本，不能直接覆盖

这就是典型的乐观锁。

所以可以把乐观锁记成一句话：

**乐观锁不是“完全不管冲突”，而是把冲突检测延迟到提交阶段。**

## 5. 为什么 Git 经常被拿来类比乐观锁

乐观锁特别适合用版本控制工具来理解。

比如在 Git 里：

- 大家可以同时修改
- 每个人先在本地改自己的内容
- 提交时再合并
- 如果没有冲突，就顺利合并
- 如果同一位置被两个人改了，就提示冲突，让你手动处理

这个过程就非常像乐观锁：

- 先不禁止并发修改
- 真正发生版本不一致时，再去检测和处理

所以 Git 的协作模型，本质上就是一种很典型的“先并行工作，提交时校验一致性”的思想。

当然，Git 不是数据库乐观锁本身，但它很好地帮助理解乐观锁的核心理念。

## 6. 购物车为什么是讲乐观锁的好例子

购物车是一个很适合讲乐观锁的业务例子。

假设一个用户同时在：

- PC 端登录
- 手机端登录

如果用悲观锁来处理购物车，你可以粗暴地规定：

- 一个端正在修改购物车时，另一个端必须完全等待

这当然能保证一致性，但体验很差，而且代价很高。

更合理的做法通常是：

- 给购物车加一个版本号

例如：

```text
cart_id = 1001
version = 8
items = [...]
```

PC 端和手机端都先读到版本 `8`。

然后：

- PC 端提交修改时，带上版本 `8`
- 手机端提交修改时，也带上版本 `8`

谁先提交成功，谁就把版本改成 `9`。

后提交的人再提交时，系统发现：

- 你基于的还是版本 `8`
- 但当前购物车已经变成版本 `9`

于是就拒绝这次提交，提示用户刷新。

这就是乐观锁在业务层很常见的用法。

### 6.1 购物车例子里为什么乐观锁更合理

因为购物车这种数据通常有两个特点：

- 冲突不是时时刻刻都发生
- 大部分用户不会在两个端上同时疯狂改同一份购物车

如果为了少数冲突场景，一上来就把修改过程全部串行化，收益并不高。

所以更合适的思路是：

- 先允许大家并发读写
- 只有提交时才检测是否冲突

这就是乐观锁比悲观锁更“轻”的地方。

## 7. 乐观锁和 CAS 的关系

前一节我们讲过 CAS。

其实乐观锁和 CAS 在思想上非常接近：

- 都假设冲突不是常态
- 都是在提交时检查状态有没有变化
- 如果状态变了，就失败并重试

差别主要在层次：

- CAS 更偏底层，通常是 CPU 原子指令层面
- 乐观锁更偏业务层、数据库层、分布式数据更新层

可以这样类比：

- CAS 比较的是“内存值有没有变”
- 乐观锁比较的是“业务版本有没有变”

所以两者不是同一个工具，但逻辑很像。

## 8. 除了集中上锁，还有没有更去中心化的同步方式

讲到这里，会自然出现一个更大的问题：

**如果每次同步都要依赖一个中心节点、一个数据库、一个锁服务，会不会又把并发瓶颈集中回去了？**

例如电商平台下单。

传统集中式系统里，通常是：

- 所有订单都经过平台中心系统
- 平台负责校验、记账、扣库存、出结果

这样做当然容易统一管理，但也带来几个问题：

- 所有并发都集中在中心系统
- 中心系统是性能瓶颈
- 中心系统也是信任中心

于是就会引出一个更激进的问题：

**能不能设计一种去中心化的方案，让业务不再完全依赖单点中心进行同步？**

这就是区块链类思路经常被引入讨论的地方。

## 9. 区块链为什么能被类比成一种去中心化并发控制方案

如果从操作系统和并发控制的角度抽象地看，区块链有一个很有意思的点：

**它不是让所有人抢着去改同一份旧数据，而是让新的事实不断追加到历史之后。**

也就是说，它的思路不是：

- 去修改过去那条记录

而是：

- 在已有历史之后，再追加一个新版本

这和乐观锁里“基于版本前进”的思想有一点相通之处。

## 10. 先从最基本的信用问题说起

假设没有平台中心系统，买家和卖家直接交易。

那首先会遇到一个最基础的问题：

**谁来保证双方说的话是真的？**

一个常见思路是：

- 买家和卖家分别对自己的交易内容签名

例如一笔交易可以抽象成：

```text
from = A, to = B, price = 10000, signature = A 的签名
from = B, to = A, object = iphone, signature = 商家的签名
```

这样做的意义是：

- 数据不只是“写了一段内容”
- 还带有“是谁确认过这段内容”的证明

所以数字签名解决的首先不是并发问题，而是：

- 身份确认
- 防抵赖
- 数据未被篡改的校验

## 11. 但光有签名，还不够解决库存和余额问题

即使双方都签过名，系统还要解决一个更现实的问题：

- A 账户里到底有没有这笔钱
- B 的库存到底还有没有这件商品

也就是说，系统仍然要有某种“事实状态”。

比如：

```text
account = alice, money = 10000
account = bob, iphone = 100
```

问题来了：

- 如果没有中心数据库，这些状态放在哪里
- 如果每个人都留自己的一份，怎么保证大家看到的是同一个历史

这时候区块链的思路就出现了。

## 12. 区块链为什么强调一条基于历史版本的事实链

区块链可以粗略理解成：

- 数据不是只保留当前快照
- 而是把一连串历史事实按顺序连起来

也就是：

- 前一个版本是后一个版本的历史
- 后一个版本是在前一个版本基础上继续追加出来的

所以它形成的是一条**基于历史版本的事实链**。

这和普通数据库里“只看当前值”很不一样。

普通数据库常常更像：

- 你只关心当前余额是多少
- 当前库存是多少

而区块链更在乎：

- 这个当前值是怎么一步一步演化来的
- 每一步演化是不是有合法签名和合法历史

## 13. 为什么说区块链不鼓励“修改旧数据”

在区块链语义里，如果 Alice 想改自己的余额，通常不是：

- 回去把某个旧区块里的值直接改掉

而是：

- 新增一个末端节点
- 用一个新的区块去表达新的事实

如果谁去改旧数据，会发生什么？

- 旧区块内容变了
- 对应摘要和签名校验就会变化
- 后面所有依赖这个历史的区块都会受影响

也就是说，一旦修改历史，后续整条链的有效性都可能崩掉。

这就是区块链“写入后难以篡改”的基础原因之一。

所以它的核心思想是：

**不要回头改历史，而是继续向历史后面追加新事实。**

## 14. 区块链如何理解成“避免修改共享状态”

从并发控制的角度看，这其实很有启发性。

传统锁模型更像是在说：

- 大家都想改同一份共享状态
- 所以必须先协调谁先改

而区块链风格更像是在说：

- 不要频繁回头覆盖旧状态
- 尽量通过追加新记录来表达变化

这其实是一种非常典型的“减少共享写冲突”的思路。

换句话说：

**如果系统设计得足够好，很多时候问题不是怎么把锁做得更强，而是怎么减少大家去争同一个可变状态。**

## 15. 区块链如何解决默认信任问题

如果有一个中心平台负责给每个用户分发数据，那么问题又回来了：

- 用户为什么要百分之百相信这个中心平台没改数据

区块链想解决的一个关键问题，就是：

- 不依赖单个中心机构来定义“什么叫真实”

如果某个节点下载到的历史数据和别人看到的不一致，它就可以：

- 通过校验签名
- 对比历史链条
- 对比其他节点的数据

来判断问题出在哪里。

所以区块链并不是“完全没有同步”，而是把同步的依据从：

- 相信中心节点

转成：

- 相信公开规则
- 相信签名校验
- 相信多数节点维护的共同历史

## 16. 区块链为什么能防止一部分欺诈行为

如果历史记录一旦写入后就很难被静默修改，那很多欺诈手段就会更难做。

例如：

- 某个平台私下修改历史订单
- 某一方偷偷改掉已确认交易
- 某个中间节点偷偷改掉金额或商品信息

只要修改会破坏签名和历史链的一致性，这种篡改就更容易被发现。

所以可以把区块链的一个核心价值概括为：

**通过“历史不可随意改写”来降低欺诈空间。**

## 17. 但区块链并没有消灭并发问题

这一点也必须讲清楚。

区块链不是说：

- 从此就没有并发控制问题了

它只是换了一种解决方式。

它仍然要回答：

- 多个新交易同时出现，先记哪一个
- 两个人同时声称自己有权花同一笔钱，怎么办
- 多个节点看到的顺序不一致，怎么办

所以区块链真正要解决的，是：

- 去中心化场景下如何达成一致历史

这本质上仍然是一种同步和并发控制问题，只不过它的对象不再是“单机内存里的临界区”，而是“分布式环境中的全局事实顺序”。

## 18. 单链为什么又会遇到性能问题

如果所有交易最后都必须串成一条全局单链，那它其实又变成：

- 所有人共享一个全局顺序

这会带来一个明显问题：

- 吞吐量有限

因为全世界所有交易都想塞进同一条顺序链里，本身就意味着一种强同步。

所以如果订单量巨大，例如每天有海量请求，单条链的处理能力就会很吃力。

这个问题和数据库里“所有写都串行化”的性能瓶颈，在抽象层面其实很像。

## 19. 为什么会出现分片、分支、逐级合并这些思路

既然全局单链太慢，就很自然会出现一些优化方向：

- 先拆分成多个区域
- 每个区域先独立处理一部分数据
- 再按时间窗口或规则逐级合并

这类思路本质上是在做：

- 局部并行
- 全局汇总

从并发设计角度看，这和很多大规模系统的思路也是一致的：

- 先把竞争拆散
- 再做更高层的聚合

这说明一个很重要的点：

**并发控制不只是在“锁的颗粒度”上做优化，也可以在“任务拆分方式”和“数据组织方式”上做优化。**

## 20. 这一节怎么和前一节连起来

前一节更多是在讲：

- 怎样控制同一时间谁能进临界区

这一节则是在讲：

- 有没有办法不让所有人都去抢同一个临界区

所以两节的关系其实很紧：

- 悲观锁是“先锁住再说”
- 乐观锁是“先操作，提交时校验版本”
- 区块链类思路是“少改历史，多追加新版本，用全局规则维护一致性”

它们本质上都是并发控制，只是切入点不同。

## 21. 这一节先记住的点

- 悲观锁假设冲突经常发生，所以先加锁再修改。
- 乐观锁假设冲突不是常态，所以允许并发执行，在提交时校验版本。
- 乐观锁最常见的实现方式就是版本号。
- Git 的协作方式很适合理解乐观锁的核心思想。
- 购物车、多端编辑、库存提交这类场景，经常适合用版本号做乐观控制。
- 乐观锁和 CAS 不是同一个工具，但都属于“提交时比较状态”的思路。
- 区块链可以被理解成一种基于历史版本追加的事实链，而不是频繁回头修改旧数据。
- 区块链解决的关键问题之一，是在去中心化环境下如何建立可验证的共同历史。
- 区块链没有消灭并发问题，只是把问题转成了“如何对全局顺序和历史达成一致”。
- 当全局单链成为瓶颈时，就会继续引出分片、分区、逐级合并等更大规模的并发优化思路。
